## 1. 需求澄清

### 功能性需求

| 需求               | 描述                                                             |
|--------------------|------------------------------------------------------------------|
| **Get / Set / Delete** | 基本键值操作，平均时间复杂度 O(1)                              |
| **TTL (Time-To-Live)** | 每个键的过期设置；键在 TTL 到期后自动删除                       |
| **驱逐策略**         | LRU、LFU、FIFO、Random、基于 TTL 的驱逐（内存满时触发）          |
| **丰富的数据结构**   | String、Hash、List、Set、Sorted Set、Bitmap、HyperLogLog          |
| **原子操作**         | INCR/DECR、CAS (Compare-And-Swap)、MULTI/EXEC 事务               |
| **Pub/Sub**          | 发布和订阅频道，用于实时消息传递                                  |
| **分布式锁**         | 支持跨客户端的分布式互斥锁                                       |
| **Scan / 迭代**      | 对键空间的非阻塞迭代                                             |

### 非功能性需求

| 需求                 | 目标                                                          |
|----------------------|---------------------------------------------------------------|
| **延迟**             | 单键操作亚毫秒级（p99 < 1 ms）                                |
| **吞吐量**           | 每节点 100K+ 操作/秒                                           |
| **可用性**           | 99.99% 正常运行时间；秒级自动故障转移                           |
| **持久性**           | 可配置 —— 从纯内存到完全持久化                                  |
| **一致性**           | 副本间最终一致性；分片内强一致性                                 |
| **可扩展性**         | 线性水平扩展；支持 100+ 节点                                    |
| **容错能力**         | 能承受节点故障、网络分区、数据中心中断                           |

### 规模估算

```
假设:
  - 总数据量:           100 TB（跨集群）
  - 每节点内存:         64 GB 可用
  - 所需节点数:         100 TB / 64 GB ≈ 1,600 个节点（仅数据）
  - 含复制（3副本）:    ~4,800 个节点实例
  - 每秒请求数:         全局 1000 万 ops/sec
  - 每节点操作数:       10M / 1,600 ≈ 6,250 ops/sec（远在能力范围内）
  - 平均键大小:         64 bytes
  - 平均值大小:         1 KB
  - 每节点键数:         64 GB / (64 B + 1 KB) ≈ 6000 万键/节点
  - 总键数:             60M * 1,600 ≈ 960 亿个键

每节点网络带宽:
  - 读多写少（80/20 比例）:  6,250 * 0.8 * 1 KB = ~5 MB/s 读取
                              6,250 * 0.2 * 1 KB = ~1.25 MB/s 写入
  - 复制流量:                 1.25 MB/s * 2 副本 = ~2.5 MB/s
  - 每节点总计:              ~8.75 MB/s（在 10 Gbps 网卡上完全可控）
```

## 2. 缓存策略（深入探讨）

### 2.1 Cache-Aside（旁路缓存/懒加载）

应用程序负责读写缓存。

**工作原理：**

1. 应用程序检查缓存中是否有数据。
2. 缓存命中时，返回数据。
3. 缓存未命中时，查询数据库。
4. 将结果写回缓存。
5. 写入时，更新数据库并失效/删除缓存条目。

```
  ┌────────────┐          ┌────────────┐          ┌────────────┐
  │            │  1. GET   │            │          │            │
  │   Client   │ -------> │   Cache    │          │  Database  │
  │            │ <------- │            │          │            │
  │            │  2. HIT   │            │          │            │
  └────────────┘          └────────────┘          └────────────┘

          --- 缓存未命中流程 ---

  ┌────────────┐          ┌────────────┐          ┌────────────┐
  │            │  1. GET   │            │          │            │
  │   Client   │ -------> │   Cache    │          │  Database  │
  │            │ <------- │  (MISS)    │          │            │
  │            │          └────────────┘          │            │
  │            │  3. Query                        │            │
  │            │ ------------------------------> │            │
  │            │ <------------------------------ │            │
  │            │  4. Result                       │            │
  │            │          ┌────────────┐          │            │
  │            │  5. SET   │            │          │            │
  │            │ -------> │   Cache    │          │            │
  └────────────┘          └────────────┘          └────────────┘
```

**适用场景：**
- 读操作远多于写操作的通用缓存场景。
- 应用程序可以容忍短时间数据过期。
- 并非所有数据都需要缓存的情况。

**优点：**
- 仅缓存被请求的数据（不浪费内存）。
- 缓存故障不会导致系统崩溃（优雅降级）。
- 实现简单。

**缺点：**
- 缓存未命中的惩罚 —— 未命中时需要三次网络往返。
- 如果数据库更新而未失效缓存，可能出现过期数据。
- 冷启动或驱逐后可能出现"缓存踩踏"风险。

**Redis 示例：**
```python
def get_user(user_id):
    # 1. 检查缓存
    cached = redis.get(f"user:{user_id}")
    if cached:
        return json.loads(cached)

    # 2. 缓存未命中 — 查询数据库
    user = db.query("SELECT * FROM users WHERE id = %s", user_id)

    # 3. 带 TTL 填充缓存
    redis.setex(f"user:{user_id}", 3600, json.dumps(user))

    return user
```

### 2.2 Read-Through（读穿透）

缓存位于应用程序和数据库之间。缓存本身负责在未命中时从数据库获取数据。

**工作原理：**

1. 应用程序始终从缓存读取。
2. 命中时，缓存返回数据。
3. 未命中时，缓存从数据库加载数据，存储后返回给应用程序。

```
  ┌────────────┐          ┌────────────────┐          ┌────────────┐
  │            │  1. GET   │                │  2. Load  │            │
  │   Client   │ -------> │  Cache Layer   │ -------> │  Database  │
  │            │          │  (with loader) │ <------- │            │
  │            │ <------- │                │  3. Data  │            │
  │            │  4. Data  │   (stores it)  │          │            │
  └────────────┘          └────────────────┘          └────────────┘
```

**适用场景：**
- 当你希望缓存层拥有数据加载逻辑时。
- 支持加载器的库如 Guava Cache、Caffeine 或相关框架。

**优点：**
- 应用代码更简单（无需处理缓存未命中逻辑）。
- 数据加载集中在缓存层。

**缺点：**
- 每个键的首次请求总是较慢（冷启动未命中）。
- 缓存与数据源紧密耦合。
- 缓存实现更复杂。

---

### 2.3 Write-Through（写穿透）

每次写入先到缓存，缓存同步写入数据库后才确认。

**工作原理：**

1. 应用程序写入缓存。
2. 缓存同步写入数据库。
3. 两者都更新完毕后返回成功。

```
  ┌────────────┐          ┌────────────┐          ┌────────────┐
  │            │  1. SET   │            │  2. Write │            │
  │   Client   │ -------> │   Cache    │ -------> │  Database  │
  │            │          │            │ <------- │            │
  │            │ <------- │            │  3. ACK   │            │
  │            │  4. ACK   │            │          │            │
  └────────────┘          └────────────┘          └────────────┘
```

**适用场景：**
- 缓存与数据库之间的数据一致性至关重要时。
- 通常与 Read-Through 搭配使用以形成完整方案。

**优点：**
- 缓存和数据库始终保持同步。
- 缓存驱逐时不会丢失数据（数据在数据库中）。

**缺点：**
- 写入延迟较高（每次操作需要两次写入）。
- 即使是很少读取的数据，每次写入都经过缓存。

---

### 2.4 Write-Behind（写回/延迟写入）

应用程序写入缓存，缓存异步批量刷新到数据库。

**工作原理：**

1. 应用程序写入缓存。
2. 缓存立即确认。
3. 缓存异步写入数据库（批量、延迟）。

```
  ┌────────────┐          ┌────────────┐   async   ┌────────────┐
  │            │  1. SET   │            │  ......>  │            │
  │   Client   │ -------> │   Cache    │  3. Batch │  Database  │
  │            │ <------- │  (buffer)  │  write    │            │
  │            │  2. ACK   │            │  ......>  │            │
  │            │ (instant) │            │           │            │
  └────────────┘          └────────────┘           └────────────┘
```

**适用场景：**
- 高写入吞吐量需求。
- 应用程序可以容忍一定的数据丢失风险。
- 写入密集型工作负载（如分析计数器、会话存储）。

**优点：**
- 写入延迟非常低。
- 批量处理显著降低数据库负载。
- 可吸收写入峰值。

**缺点：**
- 如果缓存节点在刷新前崩溃，存在数据丢失风险。
- 故障恢复复杂。
- 缓存与数据库之间是最终一致性。

---

### 2.5 Refresh-Ahead（预刷新）

缓存根据预测的访问模式，在条目过期前主动刷新。

**工作原理：**

1. 缓存跟踪每个键的访问频率。
2. 在键的 TTL 过期前，如果最近被访问过，缓存会在后台从数据库刷新。
3. 客户端始终能从缓存获取新鲜数据，无需承受未命中的延迟。

```
  ┌────────────┐          ┌────────────┐          ┌────────────┐
  │            │   GET     │            │          │            │
  │   Client   │ -------> │   Cache    │          │  Database  │
  │            │ <------- │            │          │            │
  │            │  (fast!)  │            │          │            │
  └────────────┘          │            │          │            │
                          │  TTL at    │ refresh  │            │
                          │  80%?      │ -------> │            │
                          │  Recently  │ <------- │            │
                          │  accessed? │          │            │
                          └────────────┘          └────────────┘
```

**适用场景：**
- 可预测的访问模式。
- 缓存未命中延迟不可接受时。
- 高流量热点键需要最小化过期时间。

**优点：**
- 热点键的缓存未命中率接近零。
- 频繁访问数据的延迟降低。

**缺点：**
- 刷新可能不会再被请求的数据会浪费资源。
- 实现复杂；需要预测访问模式。

---

### 2.6 策略对比表

| 策略            | 读延迟       | 写延迟        | 一致性       | 数据丢失风险   | 复杂度     | 最适用场景                    |
|-----------------|-------------|---------------|-------------|----------------|------------|------------------------------|
| Cache-Aside     | 未命中：高   | 低（仅数据库）| 最终一致     | 无             | 低         | 通用场景                      |
| Read-Through    | 未命中：高   | 不适用        | 最终一致     | 无             | 中         | 简化读取路径                  |
| Write-Through   | 命中：低     | 高            | 强一致       | 无             | 中         | 一致性关键的写入              |
| Write-Behind    | 命中：低     | 非常低        | 最终一致     | **高**         | 高         | 写入密集型工作负载            |
| Refresh-Ahead   | 非常低       | 不适用        | 近实时       | 无             | 高         | 热点键、可预测的访问          |

## 4. 数据分区

### 4.1 基于哈希的分区

最简单的方法：`node = hash(key) % N`，其中 N 是节点数量。

**问题：** 当 N 变化时（添加/移除节点），几乎所有键都会被重新映射。

```
之前（3 个节点）：  hash("user:1") % 3 = 1  -->  Node 1
之后（4 个节点）：  hash("user:1") % 4 = 2  -->  Node 2（已迁移！）

扩容时约 (N-1)/N 的键会被重新映射。
向 3 个节点中添加 1 个节点：~67% 的键必须迁移。
```

### 4.2 Consistent Hashing（深入探讨）

Consistent Hashing 将键和节点都映射到一个环形哈希空间（哈希环）上。每个键被分配给环上顺时针方向遇到的第一个节点。

```
            哈希环（0 到 2^32 - 1）

                    0 / 2^32
                      │
                ┌─────┴─────┐
               ╱              ╲
              │   Node A       │
              │   (pos: 30°)   │
             ╱                  ╲
            │                    │
   270° ────┤                    ├──── 90°
            │    key:"user:7"    │
            │    (pos: 200°)     │
             ╲                  ╱
              │   Node C       │
              │   (pos: 150°)  │
               ╲              ╱
                └─────┬─────┘
                      │
                    180°
                  Node B
                  (pos: 180°)

  Key "user:7" 在 200° --> 顺时针走 --> 到达 Node A 的 30°？
  不是！到达 Node C？让我们精确计算：

  从 200° 顺时针：270°（无节点），360°/0°（无节点），30° = Node A

  所以 "user:7" 映射到 Node A。
```

**添加节点时：**

```
  之前：A(30°), B(180°), C(150°)
  在 220° 添加 D：

  只有 180° 到 220° 之间的键从 A 迁移到 D。
  其他所有键保持在当前节点不变。

  影响：平均只有 K/N 个键需要迁移（K = 总键数，N = 节点数）。
```

**移除节点时：**

```
  移除 B(180°)：
  原本在 B 上的键（150° 到 180° 之间）现在转到 A（顺时针方向的下一个节点）。
  只有 B 的键被重新分配。
```

### 4.3 Virtual Nodes（虚拟节点）

物理节点较少时，键的分布不均匀。虚拟节点通过将每个物理节点映射到环上的多个位置来解决此问题。

```
  Physical Node A  -->  VNode A-0 (30°), A-1 (120°), A-2 (250°), A-3 (340°)
  Physical Node B  -->  VNode B-0 (60°), B-1 (170°), B-2 (280°), B-3 (50°)
  Physical Node C  -->  VNode C-0 (100°), C-1 (210°), C-2 (310°), C-3 (150°)

  带虚拟节点的哈希环：

  0°───30°(A)──50°(B)──60°(B)──100°(C)──120°(A)──150°(C)──170°(B)──
  ──210°(C)──250°(A)──280°(B)──310°(C)──340°(A)───360°/0°

  结果：分布更加均匀。
  典型配置：每个物理节点 100-200 个虚拟节点。
```

**优势：**
- 在异构硬件上实现均匀的数据分布。
- 为更强大的机器分配更多虚拟节点。
- 节点加入或离开时重新分配更平滑。

### 4.4 Redis Cluster：Hash Slot 方案

Redis Cluster 使用固定的 16,384 个 Hash Slot（而非传统的 Consistent Hashing 环）：

```
  slot = CRC16(key) % 16384

  Node A: slots 0 - 5460
  Node B: slots 5461 - 10922
  Node C: slots 10923 - 16383
```

**相对于纯 Consistent Hashing 的优势：**
- 确定性的 Slot 分配；无环歧义。
- 重新分片时迁移特定的 Slot 范围，而非随机键。
- 客户端缓存 Slot 到节点的映射，实现直连路由。

### 4.5 热点键问题及解决方案

"热点键"是指接收不成比例流量的单个键（如热门帖子、明星的个人资料）。

| 解决方案                | 描述                                                           |
|--------------------------|----------------------------------------------------------------|
| **键拆分**               | 将 `hot_key` 拆分为 `hot_key:0`、`hot_key:1`、...、`hot_key:N`。客户端随机从某个分片读取。 |
| **本地缓存**             | 在应用程序内存中缓存热点键（L1 缓存），配合短 TTL。             |
| **读副本**               | 将热点键的读请求路由到副本以分散负载。                          |
| **代理层缓存**           | 让代理检测并在本地缓存热点键。                                  |
| **键追踪**               | Redis `CLIENT TRACKING` + `REDIRECT`，用于服务端辅助的失效通知。|

```
  热点键拆分示例：

  原始：     GET celebrity:123         -->  始终命中 Node B
  拆分后：   GET celebrity:123:{0..9}  -->  分布到多个节点

  写入：
    for i in range(10):
        redis.set(f"celebrity:123:{i}", data)

  读取：
    shard = random.randint(0, 9)
    redis.get(f"celebrity:123:{shard}")
```

### 5.2 Hash Table 实现

Redis 使用带有渐进式 rehash 的哈希表：

```
  ┌──────────────────────────────────────────────┐
  │              Redis Dict（哈希表）              │
  │                                               │
  │  ht[0]（当前表）          ht[1]（rehash 目标） │
  │  ┌──────────────────┐     ┌────────────────┐  │
  │  │ bucket[0] -> E1  │     │（rehash 开始前  │  │
  │  │ bucket[1] -> E2->E5    │  为空）         │  │
  │  │ bucket[2] -> E3  │     │                │  │
  │  │ bucket[3] -> nil │     │                │  │
  │  │ bucket[4] -> E4  │     │                │  │
  │  └──────────────────┘     └────────────────┘  │
  │                                               │
  │  rehashidx: -1（未在 rehash）                  │
  │  load_factor = used / size                    │
  │  当 load_factor > 1 时触发 rehash              │
  └──────────────────────────────────────────────┘

  渐进式 Rehash：
  - Rehash 开始时，分配 ht[1]（2 倍大小）。
  - 每次操作时，将 1 个 bucket 从 ht[0] 迁移到 ht[1]。
  - Rehash 期间，读操作检查两个表；写操作写入 ht[1]。
  - 所有 bucket 迁移完成后，交换 ht[0] 和 ht[1]，释放旧表。
  - 避免了 O(N) 的阻塞式 rehash。
```

### 5.4 驱逐策略（深入探讨）

当达到 `maxmemory` 限制时，Redis 必须驱逐键以腾出空间。

| 策略                | 描述                                                          |
|---------------------|---------------------------------------------------------------|
| `noeviction`        | 写入时返回错误；读取仍然有效                                   |
| `allkeys-lru`       | 从所有键中驱逐最近最少使用的键                                 |
| `volatile-lru`      | 从设置了 TTL 的键中驱逐 LRU 键                                |
| `allkeys-lfu`       | 从所有键中驱逐最不经常使用的键                                 |
| `volatile-lfu`      | 从设置了 TTL 的键中驱逐 LFU 键                                |
| `allkeys-random`    | 随机驱逐一个键                                                |
| `volatile-random`   | 随机驱逐一个设置了 TTL 的键                                    |
| `volatile-ttl`      | 驱逐最接近过期时间的键                                        |

**Redis 配置：**
```

CONFIG SET maxmemory-policy allkeys-lru
```

### 5.5 LRU 实现：双向链表 + 哈希表

经典的 LRU 缓存使用哈希表实现 O(1) 查找，使用双向链表实现 O(1) 的驱逐排序。

```
  Hash Map                         双向链表
  ┌───────────┐                    （最近使用）           （最久未使用）
  │ key1 -> ──┼──────────────>  ┌────┐   ┌────┐   ┌────┐   ┌────┐
  │ key2 -> ──┼────────────>    │ D  │<->│ A  │<->│ C  │<->│ B  │
  │ key3 -> ──┼──────────>      │    │   │    │   │    │   │    │
  │ key4 -> ──┼────────>        └────┘   └────┘   └────┘   └────┘
  └───────────┘                   HEAD                        TAIL
                                  (MRU)                       (LRU)

  GET 键 "A"：
    1. HashMap 查找：O(1) -> 找到节点
    2. 将节点移到链表 HEAD：O(1)
    3. 返回值

  SET 新键（缓存已满）：
    1. 移除 TAIL 节点（LRU 受害者）：O(1)
    2. 从 HashMap 中移除：O(1)
    3. 在 HEAD 插入新节点：O(1)
    4. 添加到 HashMap：O(1)
```

**伪代码：**

```python
class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.cache = {}          # key -> Node
        self.head = Node(0, 0)   # dummy head（MRU 端）
        self.tail = Node(0, 0)   # dummy tail（LRU 端）
        self.head.next = self.tail
        self.tail.prev = self.head

    def get(self, key):
        if key not in self.cache:
            return -1
        node = self.cache[key]
        self._move_to_head(node)
        return node.value

    def put(self, key, value):
        if key in self.cache:
            node = self.cache[key]
            node.value = value
            self._move_to_head(node)
        else:
            if len(self.cache) >= self.capacity:
                # 驱逐 LRU（tail.prev）
                lru = self.tail.prev
                self._remove(lru)
                del self.cache[lru.key]

            new_node = Node(key, value)
            self.cache[key] = new_node
            self._add_to_head(new_node)

    def _add_to_head(self, node):
        node.prev = self.head
        node.next = self.head.next
        self.head.next.prev = node
        self.head.next = node

    def _remove(self, node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _move_to_head(self, node):
        self._remove(node)
        self._add_to_head(node)


class Node:
    def __init__(self, key, value):
        self.key = key
        self.value = value
        self.prev = None
        self.next = None
```

**注意：** Redis 并未使用真正的 LRU。它使用**近似 LRU** —— 随机采样 `maxmemory-samples`（默认 5）个键，驱逐其中访问时间最久的那个。这以少量准确性的损失换取了显著的内存节省（无需为每个键维护链表开销）。

### 5.6 LFU（最不经常使用）实现

Redis LFU 使用存储在 LRU 字段中 8 位的对数频率计数器：

```
  redisObject.lru 字段（24 位）：
  ┌────────────────────┬──────────┐
  │  上次衰减           │ 对数频率 │
  │  时间（16 位）      │ （8 位） │
  └────────────────────┴──────────┘

  频率计数器（0-255）使用对数增长：
    - P(递增) = 1 / (old_counter * lfu_log_factor + 1)
    - 默认 lfu_log_factor = 10
    - 计数器 255 代表约 100 万次访问

  衰减：计数器每 lfu_decay_time 分钟减半。
  这确保了过去热门但现在冷门的键会被驱逐。
```

## 6. 复制与高可用

### 6.1 Master-Replica 复制

```
  ┌──────────┐       复制流       ┌──────────┐
  │  Master  │ ──────────────────────────────> │ Replica 1│
  │          │                                 │ （读）    │
  │  写入    │       复制流       ┌──────────┐
  │  + 读取  │ ──────────────────────────────> │ Replica 2│
  │          │                                 │ （读）    │
  └──────────┘                                 └──────────┘

  初始同步（全量重同步）：
  1. Replica 发送 PSYNC 给 Master。
  2. Master 开始 BGSAVE（fork + 快照）。
  3. Master 将 RDB 文件发送给 Replica。
  4. Master 发送 BGSAVE 期间缓冲的写入。
  5. Replica 加载 RDB 并应用缓冲的写入。

  持续同步（增量重同步）：
  - Master 维护一个复制积压缓冲区（环形缓冲区）。
  - 每个 Replica 跟踪其复制偏移量。
  - 重连时，Replica 发送其偏移量。
  - 如果偏移量在积压缓冲区内，Master 只发送增量数据。
  - 否则，需要全量重同步。
```

### 6.2 异步 vs 同步复制的权衡

| 方面               | 异步                                  | 同步                                 |
|--------------------|---------------------------------------|--------------------------------------|
| **写入延迟**       | 低（Master 立即返回）                  | 高（等待 Replica 确认）               |
| **数据安全**       | Master 故障时有数据丢失风险            | 无数据丢失                            |
| **吞吐量**         | 更高                                  | 更低                                  |
| **可用性**         | 更高（Replica 延迟可接受）             | 更低（Replica 必须可达）              |
| **Redis 默认**     | 是（异步）                             | 否（`WAIT` 命令实现半同步）           |

**使用 WAIT 实现半同步：**
```
# 写入数据
SET user:1 "Alice"

# 等待至少 1 个 Replica 确认，超时 100ms
WAIT 1 100
# 返回：已确认的 Replica 数量
```

### 6.3 Sentinel 模式实现故障转移

Redis Sentinel 提供自动故障转移和监控。

```
  ┌──────────┐    ┌──────────┐    ┌──────────┐
  │Sentinel 1│    │Sentinel 2│    │Sentinel 3│
  │          │<-->│          │<-->│          │
  └────┬─────┘    └────┬─────┘    └────┬─────┘
       │               │               │
       │  监控          │  监控          │  监控
       │               │               │
  ┌────▼─────┐    ┌────▼─────┐    ┌────▼─────┐
  │  Master  │───>│ Replica 1│    │ Replica 2│
  │  (6379)  │───>│  (6380)  │    │  (6381)  │
  └──────────┘    └──────────┘    └──────────┘

  故障转移流程：
  ─────────────────────────────────────────────────────

  1. Sentinel 检测到 Master 宕机（SDOWN - 主观下线）。
  2. 多个 Sentinel 达成共识（ODOWN - 客观下线，达到法定人数）。
  3. 选举一个 Sentinel 作为 Leader（类 Raft 共识）。
  4. Leader 选择最佳 Replica：
     - 最高优先级（最低的 replica-priority）
     - 最多已复制数据（最高复制偏移量）
     - 最小 runid（平局时决胜）
  5. 被选中的 Replica 提升为 Master（REPLICAOF NO ONE）。
  6. 其他 Replica 被重新配置为从新 Master 复制。
  7. Sentinel 更新配置。客户端收到通知。

  时间线：
  [0s] Master 故障
  [5s] Sentinel SDOWN（在 down-after-milliseconds 之后）
  [6s] ODOWN 共识达成
  [7s] Sentinel Leader 选举完成
  [8s] 新 Master 提升
  [9s] 客户端重定向
  总计：典型故障转移时间约 10 秒
```

### 6.4 Redis Cluster 模式架构

```
  ┌──────────────────────────────────────────────────────┐
  │                Redis Cluster（6 个节点）              │
  │                                                      │
  │   Node A（master）        Node D（A 的 replica）      │
  │   Slots: 0-5460          Slots: 0-5460（副本）        │
  │                                                      │
  │   Node B（master）        Node E（B 的 replica）      │
  │   Slots: 5461-10922      Slots: 5461-10922（副本）    │
  │                                                      │
  │   Node C（master）        Node F（C 的 replica）      │
  │   Slots: 10923-16383     Slots: 10923-16383（副本）   │
  │                                                      │
  │   Gossip 协议：                                       │
  │   - 每个节点每秒 ping 随机节点                         │

  MOVED 重定向：
  Client -> Node A: GET user:500  (slot 7231)
```

### 6.5 脑裂问题

脑裂发生在网络分区导致多个节点认为自己是 Master 的情况下。

```
  分区场景：

  ┌──────────────────┐      网络        ┌──────────────────┐
  │  数据中心 1       │     分区         │  数据中心 2       │
  │                  │    ──── X ────     │                  │
  │  Master（旧）     │                    │  Replica         │
  │  Sentinel 1      │                    │  Sentinel 2      │
  │                  │                    │  Sentinel 3      │
  └──────────────────┘                    └──────────────────┘

  DC2 将 Replica 提升为新 Master（DC2 中达到法定人数）。
  DC1 的旧 Master 仍然接受写入（DC1 中的客户端可以访问）。
  两个 MASTER！数据分歧！
```

**解决方案：**

| 解决方案                             | 工作原理                                                    |
|--------------------------------------|-----------------------------------------------------------------|
| `min-replicas-to-write`             | 如果连接的 Replica 少于 N 个，Master 拒绝写入。                  |
| `min-replicas-max-lag`              | 如果 Replica 延迟超过 N 秒，Master 拒绝写入。                    |
| **基于仲裁的写入**                    | 确认写入前需要多数节点确认。                                     |
| **Fencing Token**                    | 新 Master 获得单调递增的 token；存储层拒绝旧 Master 的写入。      |
| **NODE_TIMEOUT + 集群设置**          | 调整 cluster-node-timeout 以平衡误报率和检测速度。               |

**配置：**
```
# 要求至少 1 个 Replica 且延迟 < 10 秒
CONFIG SET min-replicas-to-write 1
CONFIG SET min-replicas-max-lag 10
```

## 7. 持久化

### 7.1 快照（RDB）

RDB 创建数据集的时间点快照。

```
  ┌──────────┐    fork()     ┌──────────────┐
  │  Redis   │ ──────────>   │ 子进程        │
  │  Master  │               │              │
  │ （处理    │               │  将 RDB 文件 │
  │  请求）   │               │  写入磁盘    │
  └──────────┘               └──────┬───────┘
       │                            │
       │ Copy-on-Write (COW)        │
       │ 页面共享直到                │
       │ 被修改                     ▼
       │                      ┌──────────┐
       │                      │ dump.rdb │
       │                      │ （二进制）│
       │                      └──────────┘
       │
  时间线：
  [T0] 触发 BGSAVE（手动或通过 save 规则）
  [T0] fork() — 接近瞬时（COW，无数据复制）
  [T0-T1] 子进程将所有数据序列化到临时文件
  [T1] 将临时文件重命名为 dump.rdb（原子操作）
  [T1] 子进程退出
```

**配置：**
```
save 900 1       # 900 秒内如果有 1+ 个键变化则快照
save 300 10      # 300 秒内如果有 10+ 个键变化则快照
save 60 10000    # 60 秒内如果有 10000+ 个键变化则快照

rdbcompression yes
rdbchecksum yes
dbfilename dump.rdb
dir /var/lib/redis
```

**优点：**
- 紧凑的单文件备份，易于传输。
- 重启速度快（加载二进制文件）。
- 性能影响最小（子进程完成工作）。

**缺点：**
- 快照之间可能丢失数据（可能是几分钟）。
- 大数据集时 fork() 可能较慢（内存页表复制）。
- 内存峰值：BGSAVE 期间在大量写入下 COW 可能使内存使用翻倍。

### 7.2 Append-Only File (AOF)

AOF 记录每个写操作。

```
  ┌──────────┐   每次写入    ┌───────────────┐
  │  Redis   │ ──────────────>  │  AOF 缓冲区  │
  │  Master  │                  └───────┬───────┘
  └──────────┘                          │
                                        │ fsync 策略
                              ┌─────────▼─────────┐
                              │   appendonly.aof   │
                              │                    │
                              │ *3\r\n             │
                              │ $3\r\n             │
                              │ SET\r\n            │
                              │ $5\r\n             │
                              │ user1\r\n          │
                              │ $5\r\n             │
                              │ Alice\r\n          │
                              │ *3\r\n             │
                              │ $3\r\n             │
                              │ SET\r\n            │
                              │ ...                │
                              └────────────────────┘

  fsync 策略：
  ┌─────────────┬──────────────────────────────────────────┐
  │ always      │ 每次写入后 fsync。最安全，最慢。           │
  │ everysec    │ 每秒 fsync 一次。良好的折中方案。          │
  │ no          │ 让操作系统决定。最快，最不安全。           │
  └─────────────┴──────────────────────────────────────────┘
```

**AOF 重写（压缩）：**
```
  原始 AOF：             重写后 AOF：
  SET x 1                SET x 3
  SET x 2                SET y "hello"
  SET x 3
  SET y "hello"
  DEL z
  SET z "world"
  DEL z

  重写将历史折叠为当前状态。
  当 AOF 大小 > auto-aof-rewrite-percentage（相对于上次重写大小）时触发。
```

**配置：**
```
appendonly yes
appendfsync everysec
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

### 7.3 混合方案（RDB + AOF）

Redis 4.0+ 支持混合持久化模式：

```
  ┌────────────────────────────────────────┐
  │            混合 AOF 文件               │
  │                                        │
  │  ┌──────────────────────────────────┐  │
  │  │  RDB 前言（二进制快照）           │  │
  │  │  - 重写时的完整状态              │  │
  │  │  - 加载速度快                    │  │
  │  └──────────────────────────────────┘  │
  │  ┌──────────────────────────────────┐  │
  │  │  AOF 尾部（文本命令）             │  │
  │  │  - 快照之后的命令                │  │
  │  │  - 保持 AOF 的持久性             │  │
  │  └──────────────────────────────────┘  │
  └────────────────────────────────────────┘

  优势：
  - 重启速度快（加载 RDB 前言）
  - 最小化数据丢失（AOF 尾部包含最近的命令）
  - 两全其美
```

**配置：**
```
aof-use-rdb-preamble yes
```

### 7.4 持久化权衡

| 方面               | RDB                  | AOF (everysec)       | 混合（RDB + AOF）     |
|--------------------|----------------------|----------------------|-----------------------|
| **数据丢失**       | 数分钟的数据          | 约 1 秒的数据         | 约 1 秒的数据          |
| **重启速度**       | 快（二进制加载）      | 慢（重放日志）         | 快                    |
| **磁盘占用**       | 紧凑                 | 较大（增长快）         | 中等                  |
| **写入性能**       | 影响最小             | 略有影响              | 略有影响               |
| **备份**           | 简单（单文件）        | 较难（不断增长的日志） | 中等                  |
| **推荐场景**       | 仅缓存场景           | 数据存储场景           | 生产环境默认           |

## 8. 缓存失效

### 8.1 基于 TTL 的过期

```
# 设置带 TTL 的键
SET session:abc "data" EX 3600        # 1 小时后过期
SET temp:key "data" PX 500            # 500ms 后过期
SETEX user:cache:1 300 "profile"      # 5 分钟后过期

# 检查剩余 TTL
TTL session:abc                        # 返回秒数
PTTL session:abc                       # 返回毫秒数

# 移除过期设置
PERSIST session:abc                    # 键永不过期
```

### 8.2 主动 vs 被动过期

```
  被动（惰性）过期：
  ┌──────────┐   GET key   ┌──────────┐
  │  Client   │ ──────────> │  Redis   │
  │           │             │          │
  │           │             │ TTL 是否 │
  │           │             │ 已过期？ │
  │           │  (nil)      │ 是 ->    │
  │           │ <────────── │ 删除并   │
  └──────────┘             │ 返回 nil │
                           └──────────┘
  问题：永远不被访问的键会一直占用内存！

  主动过期（Redis 后台任务）：
  ┌─────────────────────────────────────────────┐
  │  每 100ms：                                  │
  │  1. 从设置了 TTL 的键中随机采样 20 个         │
  │  2. 删除采样中所有已过期的键                  │
  │  3. 如果超过 25% 已过期，从步骤 1 重新开始    │
  │    （循环直到低于 25% 或达到时间限制）         │
  │                                              │
  │  这以概率方式回收内存，                       │
  │  而无需扫描所有键。                           │
  └─────────────────────────────────────────────┘
```

### 8.3 事件驱动的失效

```
  ┌──────────┐  update   ┌──────────┐  invalidate  ┌──────────┐
  │  Service  │ ──────>  │ Database │ ───event───> │  Cache   │
  │    A      │          │          │              │          │
  └──────────┘          └──────────┘              └──────────┘

  实现方式：
  1. 数据库触发器 -> 消息队列 -> 缓存删除
  2. CDC（变更数据捕获）通过 Debezium/Maxwell -> 缓存删除
  3. 应用层 Pub/Sub（Redis PUBLISH）
  4. Redis Keyspace Notifications

  Redis Keyspace Notifications：
    CONFIG SET notify-keyspace-events KEA

    SUBSCRIBE __keyevent@0__:set
    SUBSCRIBE __keyevent@0__:expired
    SUBSCRIBE __keyevent@0__:del
```

### 8.4 缓存踩踏问题及解决方案

缓存踩踏（雷群效应）发生在一个热门键过期后，大量并发请求同时未命中缓存并冲击数据库。

```
  正常：       键过期 -> 1 个请求重建缓存

  踩踏：       键过期 -> 1000 个请求全部未命中 ->
               1000 个数据库查询 -> 数据库过载！

  ┌─��────────┐
  │ 请求 1   │──┐
  ├──────────┤  │         ┌──────────┐
  │ 请求 2   │──┤ 缓存    │          │    1000 个同时
  ├──────────┤  │ 未命中！ │ Database │ <── 查询！
  │ 请求 3   │──┤ ──────> │          │    数据库过载
  ├──────────┤  │         │          │
  │  ...     │──┤         └──────────┘
  ├──────────┤  │
  │ 请求 N   │──┘
  └──────────┘
```

**方案 1：互斥锁 / 分布式锁**

```python
def get_with_lock(key):
    value = redis.get(key)
    if value is not None:
        return value

    lock_key = f"lock:{key}"
    if redis.set(lock_key, "1", nx=True, ex=10):  # 获取锁
        try:
            value = db.query(key)
            redis.setex(key, 3600, value)
            return value
        finally:
            redis.delete(lock_key)
    else:
        # 另一个线程正在重建；等待后重试
        time.sleep(0.05)
        return get_with_lock(key)
```

**方案 2：提前 / 概率性过期**

```python
def get_with_early_expiry(key):
    data = redis.get(key)  # 返回 {value, ttl_set_at, actual_ttl}
    if data is None:
        return rebuild_and_cache(key)

    parsed = json.loads(data)
    remaining_ttl = parsed["actual_ttl"] - (time.time() - parsed["ttl_set_at"])
    # 概率性地在过期前刷新
    # 随着 TTL 减少，概率增加
    beta = 1  # 调节参数
    if remaining_ttl - beta * math.log(random.random()) <= 0:
        return rebuild_and_cache(key)

    return parsed["value"]
```

**方案 3：后台刷新**

```python
# 独立的工作进程
def cache_refresh_worker():
    while True:
        keys_near_expiry = get_keys_expiring_soon(threshold=60)
        for key in keys_near_expiry:
            value = db.query(key)
            redis.setex(key, 3600, value)
        time.sleep(10)
```

## 9. 一致性

### 9.1 最终一致性模型

分布式缓存本质上是最终一致的。副本落后于主节点。

```
  时间线：

  Master:   SET x=1  ──>  SET x=2  ──>  SET x=3
                  \            \             \
                   \            \             \
  Replica:  x=0 ──> x=1 ──────> x=2 ──────> x=3
                     ^           ^
                     │           │
                 复制延迟      复制延迟

  在延迟窗口内，从 Replica 读取会看到过期数据。
  典型延迟：< 1ms（同数据中心），10-100ms（跨数据中心）。
```

### 9.2 Read-Your-Writes 一致性

确保客户端始终能看到自己的写入。

```
  方法 1：粘性读取
    - 写入后，在短时间窗口内从 Master 读取。
    - 客户端跟踪"最后写入时间戳"。
    - 如果 Replica 的偏移量 < 客户端的写入偏移量，则从 Master 读取。

  方法 2：WAIT 命令
    - SET 之后，执行 WAIT 1 0（等待 1 个 Replica，无超时）。
    - 保证读取前至少 1 个 Replica 已有该数据。

  方法 3：基于版本
    - 每次写入返回一个版本/偏移量。
    - 客户端在读请求中携带版本号。
    - 如果 Replica 的版本落后，则拒绝读取；客户端回退到 Master。
```

### 9.3 缓存-数据库一致性模式

核心挑战：在并发操作期间保持缓存和数据库同步。

**问题场景（Cache-Aside）：**
```
  线程 A（读取）：           线程 B（写入）：
  1. 键 X 缓存未命中
                                2. 更新数据库：X = "new"
                                3. 删除缓存键 X
  4. 读取数据库：X = "new"？不是！
    （如果数据库读取在
     线程 B 提交之前开始，
     则读到旧值）
  5. SET 缓存 X = "old"        （过期！）
```

### 9.4 双删策略

```
  带双删的写入路径：

  1. 删除缓存键
  2. 更新数据库
  3. 短暂延迟后等待（如 500ms —— 略长于读取数据库的延迟）
  4. 再次删除缓存键（捕获步骤 1-2 窗口期间的过期读取）

  def update_with_double_delete(key, new_value):
      redis.delete(key)                        # 第一次删除
      db.update(key, new_value)                # 更新数据库
      schedule_delayed(500, redis.delete, key) # 延迟后第二次删除
```

```
  线程 A（读取）：           线程 B（写入）：
  1. 键 X 缓存未命中
                                2. 删除缓存 X（第一次删除）
                                3. 更新数据库：X = "new"
  4. 读取数据库：X = "old"
    （过期读取！）
  5. SET 缓存 X = "old"
                                6.（500ms 后）删除缓存 X（第二次删除）
  7. 下次读取：缓存未命中
  8. 读取数据库：X = "new"（正确！）
  9. SET 缓存 X = "new"

  第二次删除确保步骤 5 中的过期值被清除。
```

**替代方案：通过消息队列延迟删除**

```
  ┌────────┐ 1.Delete ┌───────┐ 2.Update ┌────────┐
  │ Service│ ───────> │ Cache │          │   DB   │
  │        │ ──────────────────────────> │        │
  │        │ 3.Publish delayed delete    │        │
  │        │ ───────> ┌─────────────┐    │        │
  └────────┘          │ 消息队列     │    └────────┘
                      │             │
                      │（500ms      │    ┌───────┐
                      │  延迟）     │──> │ Cache │
                      └─────────────┘    │DELETE │
                                         └───────┘
```

### 10.1 使用 Consistent Hashing 水平扩展

```
  添加新节点：

  之前（3 个 Master）：
  ┌─────────┐  ┌─────────┐  ┌─────────┐
  │ Node A  │  │ Node B  │  │ Node C  │

  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐

  - Slot 逐个迁移。
```


### 10.2 分片方案

```
  1. 客户端分片
  ┌──────────┐
  │  Client  │──── hash(key) ──> 路由到正确的节点
  │ （智能）  │
  └──────────┘
  优点：无代理开销，延迟最低。
  缺点：客户端必须了解拓扑；管理更困难。

  2. 基于代理的分片
  ┌──────────┐    ┌───────────┐    ┌──────────┐
  │  Client  │──> │  Proxy    │──> │ Cache    │
  │ （简单）  │    │ (twemproxy│    │ Nodes    │
  └──────────┘    │  / envoy) │    └──────────┘
                  └───────────┘
  优点：客户端简单；拓扑变更仅在代理层。
  缺点：额外跳转增加延迟；代理可能成为瓶颈/单点故障。

  3. Cluster 模式（Redis Cluster）
  ┌──────────┐    ┌──────────┐
  │  Client  │──> │ Any Node │──> MOVED/ASK 重定向
  │ （集群    │    │ in       │    （如果节点错误）
  │  感知）   │    │ cluster  │
  └──────────┘    └──────────┘
  优点：无代理；节点之间自行协调。
  缺点：多键操作限于同一 Slot。
```

**对比：**

| 方面                | 客户端分片           | 基��代理             | Cluster 模式         |
|---------------------|----------------------|----------------------|----------------------|
| 延迟                | 最低                 | +1 跳                | +重定向（罕见）       |
| 客户端复杂度        | 高                   | 低                   | 中                   |
| 拓扑变更            | 需要更新客户端       | 仅更新代理           | 自动                 |
| 多键操作            | 受限                 | 受限                 | 仅限同一 Slot        |
| 可扩展性            | 良好                 | 代理瓶颈             | 出色                 |

```
  │  - 命中率：约 95%（L1 之后）     │
  └────┬─────────────────────────────┘
       │ L2 未命中
  ┌────▼─────────────────────────────┐
  │  L3：CDN / 边缘缓存              │
  │  （用于静态/半静态数据）          │
  │  - 延迟：1-50 ms                 │
  │  - 地理分布式                    │
  └────┬─────────────────────────────┘
       │ L3 未命中
  ┌────▼─────────────────────────────┐
  │  数据库（真实数据源）             │
  │  - 延迟：5-50 毫秒               │
  │  - 始终一致                      │
  └──────────────────────────────────┘

  总体缓存命中率：1 - (1-0.80) * (1-0.95) = 99%
  只有 1% 的请求到达数据库。
```

## 12. 常见面试追问

### 12.1 如何处理缓存雪崩？

**问题：** 大量键同时过期，导致数据库请求激增。

```
  正常：     键逐渐过期 -> 数据库负载平稳
  雪崩：     批量过期 -> 所有请求冲击数据库 -> 数据库崩溃

  时间线：
  ┌──────────────────────────────────────────────┐
  │  t=0: 100 万个键被缓存，TTL=3600             │
  │  t=3600: 所有 100 万个键同时过期！            │
  │  → 100 万次缓存未命中                        │
  │  → 100 万次数据库查询                        │
  │  → 数据库过载                                │
  └──────────────────────────────────────────────┘
```

**解决方案：**

| 解决方案                    | 实现方式                                                    |
|-------------------------------|-------------------------------------------------------------|
| **随机 TTL 抖动**             | `TTL = base_ttl + random(0, jitter_range)`                  |
| **分批预热**                  | 冷启动时分批预加载缓存                                       |
| **熔断器**                    | 错误率超过阈值时停止数据库查询                                |
| **数据库限流**                | 限制并发数据库查询数量                                       |
| **降级模式**                  | 雪崩期间返回过期数据或默认值                                  |
| **多层缓存**                  | L1（本地）即使 L2（Redis）冷启动也能吸收部分负载              |

```python
import random

def set_with_jitter(key, value, base_ttl=3600, jitter=300):
    ttl = base_ttl + random.randint(0, jitter)
    redis.setex(key, ttl, value)
```

### 12.2 如何处理缓存穿透？

**问题：** 对不存在的键的请求始终未命中缓存并冲击数据库。恶意攻击者可以利用这一点。

```
  攻击者发送：GET user:-999999（不存在的用户）
  1. 缓存未命中（键不存在）
  2. 数据库未命中（用户不存在）
  3. 无法缓存（没有数据可缓存！）
  4. 重复：每次请求都冲击数据库

  这完全绕过了缓存。
```

**解决方案：**

| 解决方案              | 描述                                                           |
|-------------------------|--------------------------------------------------------------------|
| **缓存空结果**          | 对已知的未命中存储 `NULL` / 空标记，配合短 TTL                       |
| **Bloom Filter**        | 查询前检查成员资格 —— 如果不在过滤器中，跳过数据库                   |
| **输入验证**            | 拒绝明显无效的键（负数 ID、无效格式）                               |
| **限流**                | 限制每个客户端/IP 的请求数以防止滥用                                |

**Bloom Filter 方案：**

```
  ┌──────────┐   key in    ┌──────────┐   yes   ┌──────────┐
  │  Client  │ ──────────> │  Bloom   │ ──────> │  Cache   │
  │          │             │  Filter  │         │          │
  └──────────┘             └──────────┘         └──────────┘
                               │ no
                               ▼
                           返回 404
                         （完全跳过数据库）

  Bloom Filter 特性：
  - 可能有假阳性（键可能不存在但过滤器说存在）
  - 不可能有假阴性（如果过滤器说不存在，键一定不存在）
  - 空间高效：1% 假阳性率时每个元素约 1.2 字节
  - 10 亿个键：过滤器约需 1.2 GB 内存
```

```python
from pybloom_live import BloomFilter

bf = BloomFilter(capacity=100_000_000, error_rate=0.01)

# 启动时填充
for key in db.get_all_keys():
    bf.add(key)

def get_with_bloom_filter(key):
    if key not in bf:
        return None  # 确定不存在

    cached = redis.get(key)
    if cached is not None:
        return cached

    value = db.query(key)
    if value is None:
        # 缓存空值以防止重复数据库查询
        redis.setex(key, 60, "NULL_MARKER")
        return None

    redis.setex(key, 3600, value)
    return value
```

### 12.3 如何处理热点键？

**问题：** 单个键接收极高流量，使拥有该键的节点不堪重负。

**详细解决方案：**

```
  方案 1：热点键的读副本

  Client ──> random(Master, Replica1, Replica2) ──> GET hot_key
  将读取负载分散到 3 个节点而非 1 个。

  方案 2：本地缓存（L1）配合短 TTL

  ┌──────────────────────────────┐
  │  应用服务器                   │
  │  ┌────────────────────────┐  │
  │  │ 本地缓存（L1）          │  │
  │  │ hot_key -> value       │  │
  │  │ TTL: 1 秒              │  │
  │  └────────────────────────┘  │
  └──────────────────────────────┘
  99% 的请求由 L1 提供服务。每秒只有 1 个请求到达 Redis。

  方案 3：键复制 / 分片

  hot_key:0  ->  Node A
  hot_key:1  ->  Node B
  hot_key:2  ->  Node C

  客户端从 hot_key:{random(0,2)} 读取
  写入必须更新所有 N 个副本。

  方案 4：Redis CLIENT TRACKING（服务端辅助的客户端缓存）

  CLIENT TRACKING ON REDIRECT <client-id>
  - Redis 跟踪客户端本地缓存了哪些键。
  - 当键发生变化时，Redis 发送失效消息。
  - 客户端使本地副本失效。
  - 大幅减少热点键对 Redis 的负载。
```

### 12.4 如何实现分布式锁？

**简单方案（SET NX 加过期时间��：**

```python
def acquire_lock(lock_name, ttl=10):
    token = str(uuid.uuid4())
    acquired = redis.set(
        f"lock:{lock_name}",
        token,
        nx=True,   # 仅在不存在时设置
        ex=ttl     # 自动过期以防止死锁
    )
    return token if acquired else None

def release_lock(lock_name, token):
    # Lua 脚本实现原子性检查并删除
    script = """
    if redis.call("GET", KEYS[1]) == ARGV[1] then
        return redis.call("DEL", KEYS[1])
    else
        return 0
    end
    """
    redis.eval(script, 1, f"lock:{lock_name}", token)
```

**Redlock 算法（分布式、容错）：**

```
  Redlock 使用 N 个独立的 Redis Master（通常 5 个）：

  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
  │ Redis 1 │ │ Redis 2 │ │ Redis 3 │ │ Redis 4 │ │ Redis 5 │
  └─────────┘ └─────────┘ └─────────┘ └─────────┘ └─────────┘

  算法：
  1. 获取当前时间 T1。
  2. 尝试在所有 N 个实例上使用相同的键和随机值获取锁。
     每个实例使用短超时（5-50ms）。
  3. 锁获取成功条件：
     - 在多数实例（N/2 + 1 = 3）上获取成功。
     - 总耗时（T2 - T1）< 锁的 TTL。
  4. 有效锁 TTL = 原始 TTL - 已耗时间。
  5. 如果获取锁失败，在所有实例上释放。

  安全特性：
  - 互斥：只有一个客户端持有锁。
  - 容错：即使 5 个实例中有 2 个宕机仍可工作。
  - 无死锁：锁自动过期。

  争议（Martin Kleppmann 的批评）：
  - 时钟漂移可能导致安全性违规。
  - GC 暂停可能导致客户端使用已过期的锁。
  - 对正确性关键的应用，Fencing Token 更安全。
```

**Fencing Token 方案：**

```
  ┌──────────┐   acquire    ┌──────────┐   token=33  ┌──────────┐
  │ Client A │ ──────────>  │  锁      │ ──────────> │ 存储     │
  │          │              │  服务    │             │          │
  └──────────┘              └──────────┘             │ 接受     │
                                                     │ token≥33 │
  ┌──────────┐   acquire    ┌──────────┐   token=34  │          │
  │ Client B │ ──────────>  │  锁      │ ──────────> │ 接受     │
  │          │              │  服务    │             │ token≥34 │
  └──────────┘              └──────────┘             └──────────┘

  如果 Client A 在 Client B 获得 token=34 之后尝试使用 token=33，
  存储层拒绝该写入。安全性得到保证。
```

### 12.5 如何用缓存实现 Pub/Sub？

**Redis Pub/Sub：**

```
  ┌──────────┐  PUBLISH ch1 "msg"  ┌──────────┐
  │Publisher │ ──────────────────> │  Redis   │
  └──────────┘                     │          │
                                   │  将消息  │
                                   │  路由到  │
                                   │  所有    │
                                   │  订阅者  │
                                   └────┬─────┘
                            ┌───────────┼───────────┐
                            ▼           ▼           ▼
                      ┌──────────┐ ┌──────────┐ ┌──────────┐
                      │ Sub 1   │ │ Sub 2   │ │ Sub 3   │
                      │SUBSCRIBE│ │SUBSCRIBE│ │SUBSCRIBE│
                      │ ch1     │ │ ch1     │ │ ch1     │
                      └──────────┘ └──────────┘ └──────────┘
```

**命令：**
```
# 发布者
PUBLISH notifications "New order received"

# 订阅者
SUBSCRIBE notifications
PSUBSCRIBE user:*:events    # 基于模式的订阅
```

**Redis Streams（持久化、消费者组）：**

```
  ┌──────────┐  XADD stream  ┌────────────────────────────┐
  │Producer │ ──────────────> │  Redis Stream              │
  └──────────┘                │                            │
                              │  ID: 1678901234567-0       │
                              │  {"event":"order","id":42} │
                              │                            │
                              │  ID: 1678901234568-0       │
                              │  {"event":"payment","ok":1}│
                              └───────────┬────────────────┘
                                          │
                     ┌────────────────────┼────────────────────┐
                     ▼                    ▼                    ▼
              ┌────────────┐       ┌────────────┐       ┌────────────┐
              │ Consumer   │       │ Consumer   │       │ Consumer   │
              │ Group A    │       │ Group A    │       │ Group B    │
              │ Worker 1   │       │ Worker 2   │       │ Worker 1   │
              └────────────┘       └────────────┘       └────────────┘

  与 Pub/Sub 的关键区别：
  - 消息被持久化（可在重启后存活）。
  - 消费者组实现工作分配（每条消息在每个组中只处理一次）。
  - 确认机制（XACK）确保至少一次投递。
  - 可以从任意时间点重放消息。
```

**Redis Streams 命令：**
```
# 生产者
XADD mystream * event "order_created" order_id "42"

# 创建消费者组
XGROUP CREATE mystream mygroup $ MKSTREAM

# 消费者读取（阻塞）
XREADGROUP GROUP mygroup worker1 COUNT 10 BLOCK 5000 STREAMS mystream >

# 确认处理完成
XACK mystream mygroup 1678901234567-0
```
