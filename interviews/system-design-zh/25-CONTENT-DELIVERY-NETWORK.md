# 设计内容分发网络 (Cloudflare / CloudFront)

## 1. 需求澄清

### 功能性需求

| # | 需求 | 描述 |
|---|------|------|
| 1 | 内容分发 | 从靠近用户的边缘节点提供静态资源（图片、JS、CSS、视频） |
| 2 | 回源拉取 | 缓存未命中时从源站拉取内容；对已知资源主动推送内容 |
| 3 | 缓存管理 | 在边缘节点存储、提供和过期缓存内容 |
| 4 | 缓存失效 | 支持 TTL 过期、按 URL/标签手动清除以及 stale-while-revalidate |
| 5 | 基于 DNS 的路由 | 通过 GeoDNS 或 anycast 将客户端路由到最近/最快的边缘 POP |
| 6 | TLS 终结 | 在边缘使用托管证书终结 HTTPS |
| 7 | Edge Compute | 在边缘节点执行轻量级逻辑（A/B 测试、认证、重写） |
| 8 | 数据分析 | 提供每个 POP 的指标：缓存命中率、带宽、错误率、延迟 |
| 9 | 多源站支持 | 将不同的 URL 路径路由到不同的源服务器 |
| 10 | DDoS / WAF | 在边缘进行速率限制、机器人检测和 Web 应用防火墙 |

### 非功能性需求

| # | 需求 | 目标 |
|---|------|------|
| 1 | 延迟 | 全球范围内第 99 百分位到最近边缘 < 50ms |
| 2 | 缓存命中率 | 静态内容 > 95% |
| 3 | 可用性 | 99.999%（每年停机时间 < 5 分钟） |
| 4 | 吞吐量 | 全球所有 POP 每秒数百万次请求 |
| 5 | 清除传播 | 清除请求后全球传播 < 5 秒 |
| 6 | 持久性 | 缓存内容在 TTL 过期或显式清除前保持可用 |
| 7 | 可扩展性 | 每个 POP 容量水平自动扩展 |
| 8 | 安全性 | TLS 1.3、OCSP stapling、HSTS、证书自动续期 |
| 9 | 一致性 | 跨 POP 缓存失效的最终一致性 |
| 10 | 可观测性 | 实时指标、每请求日志、分布式追踪 |

### 规模估算

```
流量：
  - 全球每天 100 亿次请求
  - 100 亿 / 86,400 秒 = ~115,000 次请求/秒（平均）
  - 峰值：5 倍平均 = ~575,000 次请求/秒

缓存命中率：95%
  - 缓存命中：100 亿 * 0.95 = 95 亿次请求从边缘提供
  - 回源命中：100 亿 * 0.05 = 5 亿次请求转发到源站

带宽：
  - 平均响应大小：200 KB
  - 总数据传输：100 亿 * 200 KB = 2,000 TB/天 = ~2 EB/天（出口）
  - 回源拉取：5 亿 * 200 KB = 100 TB/天（源站出口）
  - CDN 为源站节省：95% 的带宽 = 1,900 TB/天

存储（边缘缓存）：
  - 唯一可缓存对象：~1 亿
  - 平均对象大小：200 KB
  - 总计：1 亿 * 200 KB = 20 TB
  - 分布在 ~300 个 POP：每个 POP ~67 GB 热缓存（L1 SSD）

POP（接入点）：
  - ~300 个全球 POP（类似 Cloudflare）
  - 每个 POP：50-500 台服务器，取决于流量区域

清除传播：
  - 300 个 POP 必须在 < 5 秒内收到清除信号
  - Gossip 或扇出 pub/sub 消息到所有 POP
```

## 5. 深入探讨

### 5.1 CDN 基础：为什么需要 CDN、降低延迟、节省带宽

CDN 是一个地理分布的代理服务器网络，将内容缓存到更靠近终端用户的位置。没有 CDN 的情况下，每个请求都从客户端传输到单一的源数据中心，产生：

- **网络延迟**：跨大陆的 TCP 往返时间（例如美国到亚洲 200ms）
- **带宽成本**：所有流量从源数据中心出口
- **源站过载**：每个请求直接命中源服务器

使用 CDN 后：
- 东京的用户命中东京的 POP（< 5ms 网络跳数），而不是弗吉尼亚的源站（150ms+）
- 95%+ 的请求从缓存提供，源站只看到 5% 的流量
- 带宽成本从昂贵的源站出口转移到更便宜的 CDN 批量定价

```
没有 CDN：
  客户端（东京）---[150ms RTT]--->源站（弗吉尼亚）

使用 CDN：
  客户端（东京）---[5ms RTT]---> POP（东京）---[缓存命中]---> 响应
                                              ---[缓存未命中]---> 源站（弗吉尼亚）[仅一次]
```

### 5.2 Push CDN 与 Pull CDN 模型

```
+----------------------------------------------------------------------+
|                   Push CDN 与 Pull CDN                                |
+---------------------------+------------------------------------------+
| 特性                      | Push CDN          | Pull CDN             |
+---------------------------+-------------------+----------------------+
| 内容加载                  | 客户上传          | CDN 在未命中时拉取   |
| 未命中时的初始延迟        | 无（预加载）      | 首次请求较慢         |
| 存储使用                  | 所有已上传内容    | 仅热门内容           |
| 逐出控制                  | 完全控制          | CDN 决定             |
| 最适合                    | 静态、已知内容    | 动态、长尾内容       |
| 示例                      | 软件发布          | 新闻站点、博客       |
| 源站负载                  | 推送后为零        | 缓存未命中时         |
| 复杂度                    | 较高（CI/CD）     | 较低（自动）         |
+---------------------------+-------------------+----------------------+
```

**何时使用 Push CDN：**
- 软件分发（操作系统更新、游戏补丁）——内容提前已知
- 营销活动——确保在发布前预热内容
- 视频内容——你控制编码和上传管道

**何时使用 Pull CDN：**
- 拥有数百万 URL 的网站（新闻、电商）——推送所有内容不现实
- 频繁变化的动态内容
- 长尾内容——只有部分 URL 有流量

**混合方式**（大多数生产 CDN）：默认拉取，对关键/可预测的资源进行推送。

### 5.3 基于 DNS 的路由：GeoDNS、Anycast、基于延迟的路由

#### GeoDNS

```
DNS 解析流程：

客户端（东京）
    |
    | 1. 对 cdn.example.com 进行 DNS 查询
    v
递归解析器（ISP）
    |
    | 2. 查询权威 DNS
    v
权威 DNS (GeoDNS)
    |  - 检测客户端 IP 地理位置：日本
    |  - 查找日本最近的 POP：东京 POP
    |
    | 3. 返回 A 记录：203.0.113.10（东京 POP IP）
    v
客户端向 203.0.113.10 发送 HTTPS 请求
    |
    v
东京边缘 POP
```

GeoDNS 使用 GeoIP 数据库将客户端 IP 范围映射到 POP IP。TTL 通常为 60-300 秒，以允许快速故障转移。

#### Anycast 路由

```
Anycast：多个 POP 通过 BGP 广播相同的 IP 地址。
BGP 路由自动选择拓扑上最近的 POP。

                    [IP: 1.1.1.1]
                         |
          +--------------+--------------+
          |              |              |
    [POP: NY]       [POP: London]  [POP: Tokyo]
    BGP AS 1234     BGP AS 1234    BGP AS 1234
    Announces       Announces      Announces
    1.1.1.1/32      1.1.1.1/32     1.1.1.1/32

欧洲的客户端 -> 互联网路由 -> London POP（最短 BGP 路径）
美国的客户端 -> 互联网路由 -> NY POP
亚洲的客户端 -> 互联网路由 -> Tokyo POP

优势：无需 DNS 层路由，在网络层工作。
使用者：Cloudflare、Google (8.8.8.8)、Fastly
```

#### 基于延迟的路由

DNS 解析器测量到每个 POP 的实际 RTT，并返回该解析器延迟最低的 POP 的 IP。比纯 GeoIP 更准确，但需要主动探测基础设施。

### 5.4 缓存层级：L1 边缘 -> L2 区域 -> Origin Shield -> 源站

```
带缓存层级的请求流程：

客户端请求
     |
     v
+--------------------+
|  L1 边缘缓存       |  （SSD，~67 GB，热数据，本地 <5ms）
|  例如东京 POP      |
+--------------------+
     | 命中：立即返回
     | 未命中：检查父级
     v
+--------------------+
|  L2 区域缓存       |  （SSD/NVMe，~500 GB，温数据，每个区域一个）
|  例如亚太东北      |
+--------------------+
     | 命中：返回 + 填充 L1
     | 未命中：检查 Origin Shield
     v
+--------------------+
|  Origin Shield     |  （大型 SSD/HDD，~5 TB，合并所有 POP）
|  （单一位置）      |
+--------------------+
     | 命中：返回 + 填充 L2 + L1
     | 未命中：从源站拉取
     v
+--------------------+
|  源服务器          |  （客户基础设施）
+--------------------+
     | 返回内容
     | 填充 Shield -> L2 -> L1

各层级缓存命中率（示例）：
  L1 边缘：     总请求的 85%
  L2 区域：     总请求的 7%（L1 未命中后到达）
  Origin Shield：总请求的 3%（L2 未命中后到达）
  源站：        总请求的 5%
```

分层缓存的好处：
- L1 为热门内容提供亚毫秒级缓存查找
- L2 减少同一区域多个 L1 POP 的重复拉取
- Origin Shield 确保全球每个唯一缓存未���中只向源站发送一次请求

### 5.5 缓存键设计

缓存键决定什么算作一个"唯一"的可缓存对象。

```
默认缓存键：
  scheme + host + path + query_string
  例如 https://cdn.example.com/image.jpg?size=large&format=webp

缓存键组件：

+------------------+------------------------------------------+-------------------+
| 组件             | 是否包含在缓存键中？                     | 示例              |
+------------------+------------------------------------------+-------------------+
| URL（路径）      | 始终包含                                 | /assets/logo.png  |
| 查询参数         | 可配置（白名单/黑名单）                  | ?version=3        |
| Cookie           | 通常不包含（会严重分片缓存）             | session_id        |
| Accept-Encoding  | 通过 Vary 头包含                         | gzip, br          |
| Accept           | 用于内容协商时包含                       | image/webp        |
| User-Agent       | 不包含（变体太多，命中率差）             |                   |
| X-Country-Code   | 地理个性化内容时包含                     | US                |
| Authorization    | 公共 CDN 不包含；仅私有内容             |                   |
+------------------+------------------------------------------+-------------------+

Vary 头：
  源站响应包含：Vary: Accept-Encoding, Accept
  CDN 为这些头的每个组合存储单独的缓存条目。

缓存键规范化：
  - 按字母顺序排序查询参数（a=1&b=2 == b=2&a=1）
  - scheme 和 host 转为小写
  - 从缓存键中移除追踪参数（utm_source, fbclid），但不从 URL 中移除

POP 内的一致性哈希：
  POP 内的多台缓存服务器对缓存键使用一致性哈希
  来分配对象，避免未命中时的惊群效应。

  +--------+  +--------+  +--------+  +--------+
  | Cache0 |  | Cache1 |  | Cache2 |  | Cache3 |
  | hash   |  | hash   |  | hash   |  | hash   |
  | 0-90   |  | 91-180 |  | 181-270|  | 271-360|
  +--------+  +--------+  +--------+  +--------+

  hash("/assets/logo.png") = 142 -> Cache1 处理此对象
```

### 5.6 缓存失效策略

```
+----------------------+------------------+--------------------+-------------------+
| 策略                 | 传播时间         | 使用场景           | 复杂度            |
+----------------------+------------------+--------------------+-------------------+
| TTL 过期             | 自动             | 通用               | 低                |
| URL 清除             | < 5 秒           | 立即更新           | 中                |
| 基于标签的清除       | < 5 秒           | 批量失效           | 中                |
| 前缀清除             | < 5 秒           | 目录清除           | 中                |
| stale-while-revalidate| 立即提供        | 高流量资源         | 低                |
| stale-if-error       | 立即提供         | 错误恢复           | 低                |
| 版本化 URL           | 永远不需要       | 不可变资源         | 低（部署时）      |
+----------------------+------------------+--------------------+-------------------+
```

**TTL 过期：**
```
Cache-Control: public, max-age=86400
# 86400 秒后，CDN 在下次请求时重新从源站拉取
```

**stale-while-revalidate：**
```
Cache-Control: max-age=60, stale-while-revalidate=600
# 在最多 660 秒内提供过期内容
# 当内容在 60-660 秒之间时，在后台重新验证
# 重新验证不产生延迟惩罚

时间线：
  t=0    -> 缓存新鲜，从缓存提供
  t=60   -> 缓存过期，立即提供过期内容，触发后台拉取
  t=660  -> 缓存已过期，必须等待源站拉取
```

**基于标签的清除（最强大）：**
```
1. 内容在响应时通过 CDN-Cache-Tag 头打标签：
   CDN-Cache-Tag: product-123, category-shoes, homepage

2. 当 product-123 更新时，按标签清除：
   DELETE /v1/cdn/cache/tags  { "tags": ["product-123"] }

3. CDN 在所有 POP 中清除标记为 "product-123" 的所有对象
   - 可能影响：产品页面、相关轮播、分类页面等。
```

**清除传播机制：**
```
清除服务
     |
     | 将清除事件发布到消息代理
     v
+-------------+
|  Kafka Topic |   (purge-events)
+-------------+
     |
     | 扇出到所有 POP 消费者
     +----+----+----+----+----+
     v    v    v    v    v    v
  POP1 POP2 POP3 POP4 POP5 ...（300 个 POP）
  每个 POP 有一个消费者：
    1. 接收清除事件
    2. 将缓存对象标记为过期/已删除
    3. 向清除服务确认
```

### 5.7 Origin Shield：降低源站负载

```
没有 Origin Shield：
  300 个 POP 同时缓存未命中 -> 300 个请求到源站
  （流量高峰或清除后的惊群效应）

有 Origin Shield：
  300 个 POP 未命中 -> 全部 300 个路由到单个 Origin Shield POP
  Origin Shield 将 300 个并发请求合并为 1 个源站拉取
  （请求合并/请求折叠）

  +------+  +------+  +------+
  | POP1 |  | POP2 |  | POP3 |  （全部 L1 和 L2 未命中）
  +------+  +------+  +------+
      \          |        /
       \         |       /
        v        v      v
     +------------------------+
     |    Origin Shield       |
     |  （请求合并）          |
     |  3 个请求 -> 1 次拉取  |
     +------------------------+
              |
              | 单次拉取
              v
     +------------------+
     |   源服务器       |
     +------------------+

Origin Shield 放置：
  - 选择地理上靠近源站的 POP，以降低 Shield 到源站的延迟
  - 通常与源站在同一云区域（例如 AWS us-east-1 源站使用 us-east-1）

请求合并算法：
  1. 第一个 URL 请求到达 Shield -> 转发到源站，注册为"进行中"
  2. 同一 URL 的后续请求到达 -> 等待进行中的响应
  3. 源站响应 -> Shield 缓存它，返回给所有等待的请求
  4. 后续请求 -> 从 Shield 缓存提供
```

### 5.8 边缘 TLS 终结

```
边缘 TLS 握手：

客户端（东京）
    |
    | ClientHello (TLS 1.3)
    v
东京边缘 POP
    | - 拥有 cdn.example.com 的 TLS 证书
    | - 存储在边缘内存中（证书无需磁盘 I/O）
    |
    | ServerHello + Certificate + Finished (TLS 1.3 1-RTT)
    v
客户端（加密会话已建立）
    |
    | HTTP/2 GET /assets/logo.png
    v
东京边缘 POP（从缓存提供或拉取源站）
    |
    | 注意：源站连接使用独立 TLS 或内部网络
    | 边缘到 Origin Shield：使用 mTLS 进行身份验证
    v
加密响应返回给客户端

CDN 边缘的 TLS 功能：
  - TLS 1.3：将握手减少到 1-RTT（相比 TLS 1.2 的 2-RTT）
  - 0-RTT（TLS 1.3 early data）：回访用户 0-RTT 恢复
    * 权衡：重放攻击风险，通常仅用于 GET 请求
  - OCSP Stapling：边缘在握手中包含 OCSP 响应
    * 客户端无需单独向 CA 发起 OCSP 请求（节省 RTT）
  - 会话恢复：TLS 会话票据存储在边缘
  - 证书管理：
    * 通过 ACME 协议自动化（Let's Encrypt 或 DigiCert）
    * 客户子域名使用通配符证书
    * 证书通过控制平面分发到所有 POP
    * 到期前 30 天自动续期
  - SNI（服务器名称指示）：允许每个 IP 多个证书
```

### 5.9 HTTP/2 和 HTTP/3 (QUIC)

```
HTTP/1.1 的问题：
  - 队头阻塞：请求在慢速请求后面排队
  - 无多路复用：需要多个 TCP 连接
  - 每个请求开销高（冗长的头部）

HTTP/2 的解决方案：
  - 多路复用：单个 TCP 连接上的多个流
  - 头部压缩 (HPACK)
  - 服务器推送（在浏览器请求之前推送资源）
  问题：传输层的 TCP 队头阻塞仍然存在

HTTP/3 (QUIC) 的解决方案：
  - 基于 UDP 而非 TCP
  - 每流流量控制：丢包只阻塞受影响的流
  - 回访用户 0-RTT 建立连接
  - 连接迁移：客户端 IP 变化不会断开连接
    （对于在 WiFi <-> 蜂窝网络间切换的移动客户端很重要）

CDN 边缘的 HTTP/3：
+---------------------------+    QUIC/UDP    +------------------+
|    客户端（浏览器）       | <-----------> | 边缘 POP         |
|  支持 HTTP/3？ 是/否     |               | 终结 QUIC        |
|  HTTP/3 通过 Alt-Svc：    |               | 内部使用         |
|  h3="cdn.example.com:443" |               | HTTP/2 到源站    |
+---------------------------+               +------------------+

连接迁移示例（移动端）：
  客户端使用 4G 连接到 POP（连接 ID：abc123）
  客户端切换到 WiFi（IP 变化）
  HTTP/3：连接通过连接 ID abc123 保持
  HTTP/2：连接断开，需要新的 TCP 握手（200ms 惩罚）

0-RTT 连接：
  首次访问：1-RTT QUIC 握手（类似 TLS 1.3）
  回访：0-RTT 恢复，第一个数据包携带应用数据
  权衡：重放漏洞，限制为幂等请求
```

### 5.10 Edge Compute：Workers、Lambda@Edge、WebAssembly

```
传统 CDN：
  请求 -> 缓存检查 -> 缓存命中/未命中 -> 响应
  （边缘无自定义逻辑）

Edge Compute：
  请求 -> 边缘函数 -> 缓存检查 -> 响应
  （任意代码在边缘运行，< 2ms 开销）

Edge Compute 架构：

+------------------------------------------+
|           边缘 POP                        |
|                                          |
|  +----------+     +-----------------+   |
|  | 入站     |---->| 边缘函数        |   |
|  | 请求     |     | (Isolate / WASM)|   |
|  +----------+     +-----------------+   |
|                           |             |
|                   +-------+-------+     |
|                   |       |       |     |
|               提供    缓存    转发     |
|               自定义  查找    到源站   |
|               响应                     |
+------------------------------------------+

Cloudflare Workers：V8 Isolates（不是虚拟机，不是容器）
  - 冷启动：< 0ms（Isolates 共享 V8 堆，无进程 fork）
  - 内存：每个 Isolate 128 MB
  - CPU：每个请求 50ms CPU 时间
  - 语言：JavaScript、TypeScript、WASM

Lambda@Edge：CloudFront POP 上的 Node.js / Python Lambda 函数
  - 冷启动：100-300ms（Lambda 容器启动）
  - 触发器：viewer-request、origin-request、origin-response、viewer-response

边缘 WebAssembly：
  - 在 WASM 沙箱中运行编译的 Rust/C++/Go 代码
  - 计算密集型操作接近原生性能

常见 Edge Compute 用例：
  1. A/B 测试：   将 10% 流量路由到 B 变体，无需源站逻辑
  2. 边缘认证：   在命中源站前验证 JWT/会话
  3. URL 重写：   在边缘重写 /old-path -> /new-path
  4. 地域封锁：   阻止来自特定国家的请求
  5. 机器人检测： 质询可疑模式
  6. 图片调整：   通过 WASM 在边缘调整/优化图片大小
  7. API 聚合：   在边缘组合多个源站响应

边缘 KV 存储（Cloudflare KV、CloudFront Functions + DynamoDB）：
  - 全球复制的键值存储
  - 边缘函数用于读取配置、功能标志、速率限制
  - 最终一致性（写入在 ~60 秒内传播）
```

### 5.11 视频分发：HLS/DASH、自适应码率、分块传输

```
视频分发架构：

+-------------+    上传     +------------+    转码       +------------+
|  内容       | -----------> | 接入       | ------------> | 编码       |
|  创作者     |              | 服务       |               | 集群       |
+-------------+              +------------+               +------------+
                                                                |
                                          将分片存储到 S3/源站
                                                                |
                                                                v
+------------------------------------------------------------------+
|                          CDN                                      |
|                                                                  |
|  源站 (S3)：                                                     |
|    /video/abc/manifest.m3u8        （HLS 主播放列表）            |
|    /video/abc/720p/seg001.ts       （2 秒分片）                  |
|    /video/abc/720p/seg002.ts                                     |
|    /video/abc/1080p/seg001.ts                                    |
|    /video/abc/1080p/seg002.ts                                    |
|                                                                  |
|  边缘缓存：                                                     |
|    manifest.m3u8：TTL 5 秒（频繁更新）                           |
|    seg*.ts 文件：TTL 365 天（创建后不可变）                      |
+------------------------------------------------------------------+
                    |
              客户端（浏览器/应用）
              自适应码率播放器（HLS.js / Shaka Player）

自适应码率 (ABR) 算法：
  播放器持续监控网络带宽
  网络良好（10 Mbps）-> 请求 1080p 分片
  网络降级（2 Mbps）-> 切换到 720p 分片
  网络差（500 Kbps）-> 切换到 360p 分片

  播放器决策：estimated_bandwidth * 0.8 < chosen_bitrate

HLS 与 DASH：
  HLS：Apple 标准，.m3u8 播放列表，.ts 分片
  DASH：MPEG 标准，.mpd 清单，.mp4 分片 (CMAF)
  CDN 边缘支持两者，带格式协商

视频缓存策略：
  - 分片（不可变）：Cache-Control: public, max-age=31536000, immutable
  - 清单（直播）：Cache-Control: public, max-age=2, stale-while-revalidate=60
  - 对于直播流：使用短 TTL + stale-while-revalidate

大文件分块传输：
  CDN 使用 Range 请求和分块编码：
  1. 客户端请求 /video/seg001.ts，带 Range: bytes=0-1048575
  2. CDN 检查是否有缓存的分片
  3. 未命中时，CDN 使用 Range 请求从源站拉取
  4. CDN 可以在完整分片缓存前就开始向客户端流式传输
     （字节范围缓存 + 流式传输）
```

### 5.12 CDN 边缘的 DDoS 防护

```
DDoS 防护层次：

第 3/4 层（网络层）：
  - Anycast 吸收容量型攻击（每个 POP 吸收流量）
  - BGP 黑洞路由应对极端攻击（在 ISP 层空路由）
  - 按 IP 在数据包层进行速率限制（iptables/XDP/eBPF）

第 7 层（应用层）：
  - WAF（Web 应用防火墙）：OWASP 规则、自定义规则
  - 按 IP、ASN、国家、User Agent 进行速率限制
  - 质询页面（验证码、JS 质询）应对可疑流量
  - 机器人指纹识别：TLS 指纹、浏览器指纹

+----------------------------+
|  入站请求                  |
+----------------------------+
          |
          v
+----------------------------+
|  IP 信誉检查               |  阻止已知恶意 IP
+----------------------------+
          |
          v
+----------------------------+
|  速率限制器                |  每个 IP 滑动窗口 10,000 次请求/分钟
+----------------------------+
          |
          v
+----------------------------+
|  WAF 规则                  |  SQL 注入、XSS、RCE 模式
+----------------------------+
          |
          v
+----------------------------+
|  机器人检测                |  JS 质询、验证码、TLS 指纹
+----------------------------+
          |
          v
+----------------------------+
|  边缘缓存/源站            |  只有合法流量到达这里
+----------------------------+

Anycast DDoS 吸收：
  攻击产生 10 Tbps 流量
  流量通过 anycast 分布到 300 个 POP
  每个 POP 处理 10 Tbps / 300 = ~33 Gbps（在容量范围内）
  容量型攻击被吸收；没有单个 POP 被压垮

速率限制算法：
  - 令牌桶：允许突发，适合 API 速率限制
  - 滑动窗口：平滑的速率执行
  - 固定窗口：简单、成本低，但允许边界处突发
```

### 5.13 缓存命中率优化

```
目标：静态内容缓存命中率 > 95%

降低缓存命中率的因素：
  1. 查询字符串泛滥：/img.jpg?ts=1234567890（每个请求唯一）
  2. Cookie 键缓存：每个用户会话 = 唯一缓存条目
  3. 低 TTL：TTL 太短导致频繁回源
  4. 低热度：长尾内容频繁未命中
  5. 缓存逐出：LRU 逐出在内容再次被请求前移除内容

优化技术：

1. 查询参数规范化和剥离：
   - 识别追踪参数：utm_*、fbclid、gclid
   - 从缓存键中剥离（但转发到源站用于分析）
   - 按字母顺序排序剩余参数：b=2&a=1 -> a=1&b=2

2. 缓存预热（预填充）：
   - 在部署新内容前，CDN 主动拉取
   - 使用 sitemap.xml 发现需要预热的 URL
   - 对发布活动或营销活动特别重要

3. 预取：
   - 分析访问模式：如果请求了 /page/1，预取 /page/2
   - 边缘函数可以在缓存命中时触发异步预取

4. 长尾内容策略：
   - 长尾：80% 的 URL 获得 < 1% 的流量
   - 策略：不要尝试缓存所有长尾内容，聚焦前 20%
   - 使用更大的 L2/Shield 缓存以更少的回源处理长尾

5. 缓存键调优：
   - 将 Vary 头字段减少到最少必要
   - 在缓存键中使用 Accept-Encoding 但进行规范化（gzip 与 br -> 两个条目）

6. 监控和告警：
   - 缓存命中率低于 90% 时告警（可能是查询字符串攻击）
   - 按内容类型监控（图片应接近 99%，HTML 接近 80%）

按内容类型的预期命中率：
  静态图片（带哈希的不可变）：99%+
  CSS/JS（版本化）：          99%+
  HTML 页面：                 70-85%
  API 响应：                  20-60%
  个性化内容：                0%（不缓存）
```

### 5.14 多 CDN 策略

```
多 CDN 架构：

+---------------------------+
|   流量控制器              |
|   （基于 DNS 的调度）     |
+---------------------------+
     |         |        |
     v         v        v
+---------+ +--------+ +-------+
| CDN A   | | CDN B  | | CDN C |
|（主要） | |（备用  | |（低   |
|Cloudflare| |Fastly）| |成本） |
|         | |        | |AWS CF |
+---------+ +--------+ +-------+

流量调度决策：
  - 健康检查：如果 CDN A 错误率高 -> 切换到 CDN B
  - 成本：将低优先级流量路由到最便宜的 CDN
  - 地理：CDN A 用于美国，CDN B 用于欧洲，CDN C 用于亚太
  - 性能：真实用户监控 (RUM) 选择延迟最低的 CDN

基于 RUM 的调度：
  1. 客户端加载页面，向分析系统报告 CDN 延迟
  2. 分析系统按区域、ISP、CDN 聚合
  3. 流量控制器每分钟更新 DNS 权重
  4. 客户端被引导到其上下文中性能最佳的 CDN

故障转移流程：
  CDN A 健康检查失败（状态 > 5% 错误率）
  -> 流量控制器更新 DNS TTL=0（或使用 anycast 切换）
  -> CDN B 开始接收流量
  -> 向运维团队发送告警
  -> CDN A 恢复 -> 逐步切回流量（金丝雀：10% -> 50% -> 100%）

好处：
  - 冗余：CDN 中断不会导致服务下线
  - 成本：利用多个 CDN 定价模型
  - 覆盖：不同 CDN 可能在特定区域有更好的覆盖
  - 谈判：利用 CDN 供应商之间的竞争
```

## 6. 扩展策略

### POP 内的水平扩展

```
负载均衡器 (L4)
     |
     +------+------+------+
     |      |      |      |
  Server1 Server2 Server3 ...ServerN

服务器是无状态的（缓存通过一致性哈希共享）。
随着流量增长添加服务器；一致性哈希最小化缓存波动。
```

### 添加新 POP

```
添加新 POP 的流程：
  1. 在新数据中心配置物理服务器
  2. 安装 CDN 边缘软件
  3. 在控制平面注册 POP（配置、路由规则）
  4. 与本地 ISP 进行 BGP 对等（anycast 路由生效）
  5. 配置父 POP（L2 区域或 Origin Shield）
  6. POP 开始接收流量（预热期：L1 缓存填充）
  7. 监控缓存命中率、延迟、错误率

POP 放置策略：
  - 一级：主要大都市区（纽约、伦敦、东京、新加坡、法兰克福）
  - 二级：次要城市（亚特兰大、阿姆斯特丹、悉尼、孟买）
  - 三级：特定 ISP（在主要 ISP 网络内 = 用户端 POP）
  - 在高流量区域密集部署可将延迟降至 < 10ms
```

### 缓存存储扩展

```
SSD 分层：
  热数据：NVMe SSD（快速、昂贵，每节点 ~10 TB）
  温数据：SATA SSD（中等、更大，每节点 ~100 TB）
  冷数据：HDD（慢、便宜，每节点 ~1 PB）

缓存逐出：
  每个层级使用 LRU（最近最少使用）
  对象提升：HDD -> SSD（访问时）
  对象降级：SSD -> HDD（SSD 满时）
```

## 7. 成本模型

### 带宽定价

```
CDN 带宽成本（典型）：
  - CDN 到客户端的出口：$0.008/GB（批量定价，比云出口便宜约 80%）
  - 源站到 CDN 的出口：$0.09/GB（云提供商定价，例如 AWS S3）
  - CDN POP 之间：几乎免费（CDN 内部网络）

我们规模的成本计算：
  总出口：2,000 TB/天 = 2,000,000 GB/天
  CDN 成本：2,000,000 GB * $0.008 = $16,000/天 = $480,000/月

  不使用 CDN（源站出口）：
  总出口：2,000 TB/天，按 $0.09/GB = $180,000/天 = $5,400,000/月

  节省：$5,400,000 - $480,000 = $4,920,000/月（91% 节省）

  回源拉取出口（5% 的流量）：
  100 TB/天 * $0.09/GB = $9,000/天 = $270,000/月
```

### 请求定价

```
CDN 请求定价（典型）：
  HTTP 请求：$0.0075 / 10,000 次请求
  HTTPS 请求：$0.010 / 10,000 次请求

请求成本：
  每天 100 亿次请求 = 1,000,000 个 10,000 次批次
  成本：1,000,000 * $0.010 = $10,000/天 = $300,000/月

Edge Compute（Cloudflare Workers 定价）：
  每天前 100K 次请求：免费
  额外：$0.50 / 100 万次请求

预估每月 CDN 总成本：
  带宽：      $480,000
  请求：      $300,000
  Edge Compute：$50,000
  其他开销：  $50,000
  总计：      ~$880,000/月

与不使用 CDN 的源站服务相比：~$5,400,000/月
净节省：~$4,520,000/月（84% 节省）
```

## 8. 权衡分析

```
+------------------------------------------+-----------------------------+-----------------------------+
| 决策                                     | 选项 A                      | 选项 B                      |
+------------------------------------------+-----------------------------+-----------------------------+
| 缓存一致性 vs 可用性                    | 短 TTL（强一致性）          | 长 TTL + 清除 API           |
|                                          | + 频繁回源                  | + 清除失败时的过期风险      |
+------------------------------------------+-----------------------------+-----------------------------+
| Anycast vs GeoDNS 路由                   | Anycast（网络层）           | GeoDNS（DNS 层）            |
|                                          | + 自动，无 DNS TTL          | + 更多控制，更简单          |
|                                          | - 需要 BGP 对等             | - DNS TTL 限制故障转移      |
+------------------------------------------+-----------------------------+-----------------------------+
| Push vs Pull CDN                         | Push：预填充                | Pull：按需                  |
|                                          | + 无冷启动延迟              | + 更简单的部署              |
|                                          | - 需要 CI/CD 集成           | - 首次请求延迟              |
+------------------------------------------+-----------------------------+-----------------------------+
| Origin Shield：单区域 vs 多区域          | 单个 Origin Shield          | 多区域 Shield               |
|                                          | + 最大合并效果              | + 更低的 Shield 到源站 RTT  |
|                                          | - 单点故障                  | - 更高复杂度                |
+------------------------------------------+-----------------------------+-----------------------------+
| 缓存键：包含/排除查询参数               | 包含所有参数                | 仅白名单已知参数            |
|                                          | + 每个变体正确缓存          | + 更好的命中率              |
|                                          | - 命中率差（长尾）          | - 内容错误的风险            |
+------------------------------------------+-----------------------------+-----------------------------+
| TLS 终结：边缘 vs 透传                  | 边缘 TLS 终结              | SSL 透传到源站              |
|                                          | + CDN 可读取/缓存 HTTP     | + 端到端加密                |
|                                          | + 证书在 CDN 管理          | - CDN 无法缓存              |
+------------------------------------------+-----------------------------+-----------------------------+
| Edge Compute：V8 Isolates vs 容器       | V8 Isolates（冷启动：0ms） | 容器（冷启动：100ms+）      |
|                                          | + 无冷启动                  | + 完整运行时，任意语言      |
|                                          | - 仅 JS/WASM               | - 冷启动延迟                |
+------------------------------------------+-----------------------------+-----------------------------+
```

## 9. 常见面试追问

**问：如何处理缓存踩踏（惊群效应）？**

```
问题：10,000 个客户端同时请求同一 URL，全部缓存未命中，
     10,000 个请求同时命中源站。

解决方案：
1. 请求合并（加锁）：
   - 第一个请求获取该缓存键的锁
   - 后续请求等待锁
   - 源站只收到 1 个请求
   - 所有等待者收到缓存的响应

2. 概率性提前重验证：
   - 当缓存 TTL 在过期前 10% 范围内时，随机重新验证
   - 避免同步过期

3. TTL 抖动：
   - 不使用 TTL=3600，而是使用 TTL = 3600 + random(0, 600)
   - 将过期分散到时间窗口内

4. Origin Shield：
   - 所有 300 个 POP 在 Shield 合并，Shield 向源站发送单个请求
```

**问：如何实现 < 5 秒的实时清除传播？**

```
架构：
1. 清除 API 接收请求
2. 将清除事件写入 Kafka（低延迟：< 1ms）
3. 每个 POP 有专用的 Kafka 消费者
4. 消费者接收事件，标记对象为过期：< 100ms
5. 总计：1ms + 消费者延迟 + 网络 RTT

每个 POP 的 Kafka 消费者：
  - 每个 POP 专用消费者组
  - Topic 分区以实现并行
  - 至少一次交付（幂等清除操作）

备用方案：轮询
  如果 Kafka 消费者宕机，POP 每 30 秒轮询清除 API
  （最终一致性，但限制在 30 秒窗口内）
```

**问：如何处理 CDN 上的私有/认证内容？**

```
选项：
1. 签名 URL：
   - 源站生成带 HMAC 签名 + 过期时间的 URL
   - CDN 在边缘验证签名（边缘函数）
   - URL：/protected/video.mp4?expires=1709250000&sig=abc123
   - CDN 在签名 URL 缓存键下缓存内容
   - 每个用户单独缓存？不 -> 在未签名键下缓存，
     单独验证签名

2. 边缘认证：
   - 边缘函数验证 JWT/会话令牌
   - 令牌有效：提供缓存的（共享）内容
   - 令牌无效：返回 401

3. 基于 Authorization 的 Vary（不推荐）：
   - CDN 为每个 Authorization 头存储单独的缓存条目
   - 缓存命中率接近 0%（每个用户唯一）
   - 永远不要用于高流量内容
```

**问：CDN 如何与 Service Worker 交互？**

```
客户端缓存 vs CDN 缓存：
  Service Worker（客户端）：浏览器端缓存，离线支持
  CDN（网络）：共享缓存，所有用户受益

  两者同时存在时的请求流程：
  浏览器请求
    -> Service Worker 缓存（命中：返回，未命中：继续）
    -> CDN 边缘缓存（命中：返回，未命中：继续）
    -> 源站

  CDN 的 cache-control 必须与 Service Worker 策略兼容。
  对 CDN 缓存的资源使用 Vary: Accept-Encoding，但不使用 Vary: Cookie。
```

**问：如何处理缓存键冲突或缓存投毒？**

```
缓存投毒攻击：
  攻击者发送：GET /page HTTP/1.1
                  Host: cdn.example.com
                  X-Forwarded-Host: evil.com

  如果 CDN 将 X-Forwarded-Host 包含在缓存键和响应中：
  下一个用户的响应将包含 evil.com 的内容。

预防措施：
1. 在缓存前剥离危险头（X-Forwarded-Host、X-Original-URL）
2. 验证缓存键头在白名单中
3. 不要在缓存的响应体中反射请求头
4. 使用严格的缓存键定义（仅 URL + 白名单头）

Web 缓存欺骗：
  攻击者诱骗用户请求：/account?/style.css
  CDN 将其作为静态 CSS 文件缓存（基于 .css 扩展名）
  其他用户收到受害者的账户数据。

预防措施：
1. 检查响应的 Content-Type，而非 URL 扩展名
2. 只缓存具有可缓存 Content-Type 的响应（image/*、text/css 等）
3. 在存储前验证响应的 Cache-Control 允许缓存
```

**问：如何在 CDN 边缘实现地理限制？**

```
边缘函数（Cloudflare Workers 示例）：

addEventListener('fetch', event => {
  event.respondWith(handleRequest(event.request))
})

async function handleRequest(request) {
  const country = request.cf.country  // Cloudflare 提供 GeoIP
  const blockedCountries = ['CN', 'RU', 'KP']  // 从 KV 存储获取

  if (blockedCountries.includes(country)) {
    return new Response('Content not available in your region', {
      status: 451,  // HTTP 451: Unavailable For Legal Reasons
      headers: { 'Content-Type': 'text/plain' }
    })
  }

  return fetch(request)  // 转发到缓存/源站
}
```

**问：如何在 CDN 中测量和优化首字节时间 (TTFB)？**

```
TTFB 组成：
  1. DNS 解析：         5-50ms（GeoDNS 查找）
  2. TCP 连接：         1-20ms（附近 POP）
  3. TLS 握手：         5-20ms（TLS 1.3 1-RTT）
  4. HTTP 请求：        1-5ms
  5. 缓存查找：        < 1ms（SSD）
  6. 响应传输：         取决于对象大小

优化：
  - Preconnect：提示浏览器预连接到 CDN 域名
    <link rel="preconnect" href="https://cdn.example.com">
  - HTTP/2 服务器推送：CDN 推送关键资源
  - TLS 0-RTT：为回访客户端消除 TLS 握手
  - Keep-alive：为多个请求复用 TCP 连接
  - HTTP/3：完全消除 TCP 握手，使用 UDP

目标 TTFB 分解：
  DNS：        20ms（首次请求后缓存）
  TCP+TLS：    15ms（会话恢复时：0ms）
  请求：       2ms
  缓存查找：   1ms
  总计：       ~38ms（远低于缓存命中的 50ms SLA）
```

**问：解释 CDN 如何处理 WebSocket 和 Server-Sent Events。**

```
标准 CDN 缓存不适用于 WebSocket（有状态、双向）。

CDN 中的 WebSocket：
  - CDN 充当透明 TCP 代理
  - 从 HTTP 升级到 WebSocket（101 Switching Protocols）
  - 维护到源站的长连接 TCP 连接
  - CDN 增加的价值：TLS 终结、DDoS 防护、负载均衡
  - 不进行缓存

Server-Sent Events (SSE)：
  - 从服务器到客户端的单向流式传输
  - Content-Type: text/event-stream
  - CDN 转发流但无法缓存（流式响应）
  - 部分 CDN 支持边缘 SSE：通过 KV/Pub-Sub 在边缘生成事件
    （例如 Cloudflare Durable Objects）

建议：
  - 实时数据：通过 CDN 作为代理使用 SSE 或 WebSocket
  - 边缘规模的 pub/sub：Cloudflare Durable Objects / Fastly Fanout
  - 缓存可缓存的（静态资源），流式传输必须流式传输的
```
