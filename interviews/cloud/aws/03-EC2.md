# Elastic Compute Cloud (EC2)

EC2 gives you **virtual machines** (instances) in the cloud that you fully control. You choose the OS, the instance size, the networking, and the storage. EC2 is the oldest and most fundamental AWS compute service -- most other services (ECS, EKS, EMR, SageMaker) run on EC2 under the hood. Use EC2 when you need full control over the runtime environment, when your workload does not fit neatly into Lambda's constraints (15-minute timeout, 10 GB memory, limited runtimes), or when you need persistent long-running processes.

---

## 1. When to Use EC2 vs Alternatives

| Factor | EC2 | Lambda | ECS/Fargate |
|--------|-----|--------|-------------|
| Control | Full OS access | No OS access | Container-level |
| Startup time | Minutes | Milliseconds to seconds | Seconds |
| Max duration | Unlimited | 15 minutes | Unlimited |
| Pricing model | Per-second (min 60s) | Per-invocation + duration | Per-second (Fargate) or EC2-backed |
| Scaling | ASG (minutes) | Instant (concurrent executions) | Service auto scaling (seconds) |
| Best for | Stateful apps, legacy, GPU, custom kernels | Event-driven, APIs, glue code | Microservices, web apps |
| Operational burden | High (patching, AMIs, scaling) | Very low | Medium |

**Rule of thumb:** Start with Lambda or Fargate. Move to EC2 only when you hit a wall.

## 2. Instance Types and Naming Convention

EC2 instance names follow a pattern:

```
m5.xlarge
│ │  │
│ │  └─ Size: nano, micro, small, medium, large, xlarge, 2xlarge, ...
│ └──── Generation: 5th generation
└────── Family: m = general purpose
```

Additional modifiers appear between generation and size:

```
c6g.large     --> g = Graviton (ARM) processor
m5a.large     --> a = AMD processor
r6i.large     --> i = Intel processor
c5n.large     --> n = enhanced networking
m5d.large     --> d = local NVMe instance store
```

## 3. Instance Families

### 3.1 Overview

| Family | Letter | Optimized For | Example Use Case |
|--------|--------|--------------|------------------|
| General Purpose | M, T | Balanced compute/memory/network | Web servers, small DBs, dev environments |
| Compute Optimized | C | High-performance CPUs | Batch processing, ML inference, gaming, video encoding |
| Memory Optimized | R, X, z | Large memory footprint | In-memory DBs, real-time analytics, SAP HANA |
| Storage Optimized | I, D, H | High sequential read/write to local storage | Data warehouses, distributed file systems, HDFS |
| Accelerated Computing | P, G, Inf, Trn | GPU / custom hardware | ML training (P), graphics rendering (G), ML inference (Inf) |

### 3.2 The T-Series (Burstable)

T-series instances (T3, T3a, T4g) use a **CPU credit model**:

- Baseline: a guaranteed percentage of CPU (e.g., T3.micro = 10% of one vCPU)
- Credits: you earn credits when below baseline, spend them when above
- If credits run out: performance drops to baseline (or you pay extra with `unlimited` mode)

```
T3.micro baseline: 10% CPU
  - Idle for 1 hour -> earns credits
  - Spike to 100% CPU -> burns credits
  - Credits exhausted -> throttled to 10%
```

**When to use:** Dev/test, low-traffic web servers, bastion hosts. **Never** for consistent production workloads -- use M-series instead.

### 3.3 Graviton (ARM) Instances

Graviton instances (suffix `g`: M6g, C7g, R7g) are AWS-designed ARM processors. They offer up to 40% better price-performance than equivalent Intel instances. Most Linux workloads run without modification. Check your dependencies for ARM compatibility before migrating.

## 4. AMIs (Amazon Machine Images)

An AMI is a **template** for launching instances. It contains the OS, preinstalled software, and configuration.

### 4.1 AMI Types

| Type | Description |
|------|-------------|
| AWS-provided | Amazon Linux, Ubuntu, Windows Server, etc. |
| Marketplace | Third-party AMIs (some free, some paid) |
| Community | Public AMIs shared by other users (use cautiously) |
| Custom | Your own AMI built from a running instance |

### 4.2 Creating Custom AMIs

```bash
# Create an AMI from a running instance
aws ec2 create-image \
  --instance-id i-0abc123 \
  --name "my-app-v2.1.0-2024-01-15" \
  --description "App server with Node 20, nginx, monitoring agents" \
  --no-reboot

# List your AMIs
aws ec2 describe-images --owners self \
  --query 'Images[].{ID:ImageId,Name:Name,Created:CreationDate}' \
  --output table

# Copy AMI to another region (for multi-region deployment)
aws ec2 copy-image \
  --source-image-id ami-0abc123 \
  --source-region us-east-1 \
  --region eu-west-1 \
  --name "my-app-v2.1.0-eu"
```

**Best practice:** Bake your application and dependencies into a custom AMI ("golden AMI" pattern). This makes launches faster and more reliable than bootstrapping everything via user data scripts.

## 5. Launching Instances

### 5.1 Key Pairs

EC2 uses SSH key pairs for Linux access. AWS stores the public key; you download the private key once.

```bash
# Create a key pair
aws ec2 create-key-pair --key-name my-key \
  --query 'KeyMaterial' --output text > my-key.pem
chmod 400 my-key.pem

# SSH into the instance
ssh -i my-key.pem ec2-user@<public-ip>
```

### 5.2 User Data Scripts

User data runs **once** at first boot. Use it for lightweight bootstrapping.

```bash
#!/bin/bash
yum update -y
yum install -y httpd
systemctl start httpd
systemctl enable httpd
echo "<h1>Hello from $(hostname)</h1>" > /var/www/html/index.html
```

```bash
# Launch with user data
aws ec2 run-instances \
  --image-id ami-0abc123 \
  --instance-type t3.micro \
  --key-name my-key \
  --security-group-ids sg-0abc123 \
  --subnet-id subnet-0abc123 \
  --user-data file://bootstrap.sh \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=web-1}]'
```

### 5.3 Security Groups

Assign one or more security groups at launch. These control inbound and outbound traffic. See the VPC guide for details.

## 6. EBS Volumes

Elastic Block Store (EBS) provides **persistent block storage** for EC2 instances. Think of it as a virtual hard drive that persists independently of the instance lifecycle.

### 6.1 Volume Types

| Type | Code | IOPS | Throughput | Use Case |
|------|------|------|------------|----------|
| General Purpose SSD | **gp3** | 3,000 baseline (up to 16,000) | 125 MB/s (up to 1,000) | Boot volumes, most workloads |
| Provisioned IOPS SSD | **io2** | Up to 64,000 | Up to 1,000 MB/s | Databases needing consistent low latency |
| Throughput Optimized HDD | **st1** | Up to 500 | Up to 500 MB/s | Big data, data warehouses, log processing |
| Cold HDD | **sc1** | Up to 250 | Up to 250 MB/s | Infrequent access, lowest cost |

**gp3 is the default and the right choice 90% of the time.** It decouples IOPS and throughput from volume size (unlike gp2 where you needed a bigger disk to get more IOPS).

### 6.2 Key EBS Operations

```bash
# Create a volume
aws ec2 create-volume \
  --volume-type gp3 \
  --size 100 \
  --iops 3000 \
  --throughput 125 \
  --availability-zone us-east-1a \
  --encrypted

# Attach to an instance
aws ec2 attach-volume \
  --volume-id vol-0abc123 \
  --instance-id i-0abc123 \
  --device /dev/xvdf

# Create a snapshot (backup)
aws ec2 create-snapshot \
  --volume-id vol-0abc123 \
  --description "Daily backup 2024-01-15"

# Create a volume from a snapshot (restore or clone)
aws ec2 create-volume \
  --snapshot-id snap-0abc123 \
  --volume-type gp3 \
  --availability-zone us-east-1a
```

### 6.3 EBS Encryption

- EBS encryption uses AWS KMS keys
- Enable encryption by default in your account settings
- Encrypted volumes can only be attached to instances that support encryption (all modern instance types do)
- Snapshots of encrypted volumes are automatically encrypted
- You cannot un-encrypt a volume; instead, create an unencrypted copy of the snapshot and create a new volume

### 6.4 Instance Store vs EBS

| Aspect | EBS | Instance Store |
|--------|-----|----------------|
| Persistence | Survives stop/start | **Lost on stop/terminate** |
| Performance | Network-attached | Physically attached NVMe (very fast) |
| Use case | OS, databases, anything that must persist | Temporary caches, scratch data, buffers |
| Backup | Snapshots | You must replicate data yourself |

**Rule:** If you cannot afford to lose the data, use EBS. Instance store is ephemeral.

## 7. Elastic IPs

An Elastic IP is a **static public IPv4 address** that you own until you release it. You can associate it with any instance in your account.

```bash
# Allocate an Elastic IP
aws ec2 allocate-address --domain vpc

# Associate with an instance
aws ec2 associate-address \
  --allocation-id eipalloc-0abc123 \
  --instance-id i-0abc123

# Release when done (you pay for unassociated EIPs)
aws ec2 release-address --allocation-id eipalloc-0abc123
```

**Gotcha:** AWS charges for Elastic IPs that are **not associated** with a running instance. Always release EIPs you are not using.

## 8. Placement Groups

Placement groups control how instances are physically placed on underlying hardware.

| Strategy | Behavior | Use Case |
|----------|----------|----------|
| **Cluster** | Instances packed close together in one AZ | Low-latency HPC, tightly coupled workloads |
| **Spread** | Each instance on separate hardware (max 7 per AZ) | Critical instances that must not share failure domains |
| **Partition** | Instances divided into partitions on separate racks | Large distributed workloads (HDFS, Cassandra, Kafka) |

```bash
# Create a cluster placement group
aws ec2 create-placement-group \
  --group-name hpc-cluster \
  --strategy cluster

# Launch into the placement group
aws ec2 run-instances \
  --placement GroupName=hpc-cluster \
  --instance-type c5n.18xlarge \
  --count 10 \
  ...
```

## 9. Auto Scaling Groups (ASG)

An ASG automatically maintains a fleet of EC2 instances: launching new ones when demand increases and terminating them when demand decreases.

### 9.1 Components

```
Launch Template  --> defines WHAT to launch (AMI, instance type, key pair, SG, user data)
Auto Scaling Group --> defines WHERE and HOW MANY (subnets, min/max/desired, scaling policies)
Scaling Policy   --> defines WHEN to scale (CPU > 70%, request count, schedule, etc.)
```

### 9.2 Launch Templates

```bash
# Create a launch template
aws ec2 create-launch-template \
  --launch-template-name my-app-lt \
  --launch-template-data '{
    "ImageId": "ami-0abc123",
    "InstanceType": "t3.medium",
    "KeyName": "my-key",
    "SecurityGroupIds": ["sg-0abc123"],
    "UserData": "'"$(base64 bootstrap.sh)"'",
    "TagSpecifications": [{
      "ResourceType": "instance",
      "Tags": [{"Key": "Name", "Value": "my-app"}]
    }]
  }'
```

### 9.3 Creating an ASG

```bash
aws autoscaling create-auto-scaling-group \
  --auto-scaling-group-name my-app-asg \
  --launch-template LaunchTemplateName=my-app-lt,Version='$Latest' \
  --min-size 2 \
  --max-size 10 \
  --desired-capacity 2 \
  --vpc-zone-identifier "subnet-1a,subnet-1b,subnet-1c" \
  --target-group-arns arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/my-tg/abc123 \
  --health-check-type ELB \
  --health-check-grace-period 300
```

### 9.4 Scaling Policies

| Type | How It Works | Example |
|------|-------------|---------|
| **Target Tracking** | Maintain a metric at a target value | Keep average CPU at 50% |
| **Step Scaling** | Add/remove instances based on alarm thresholds | +2 instances when CPU > 70%, +4 when > 90% |
| **Scheduled** | Scale at predetermined times | Scale up at 8 AM, down at 8 PM |
| **Predictive** | ML-based forecasting from historical patterns | Auto-predicts traffic spikes |

```bash
# Target tracking policy: keep CPU at 50%
aws autoscaling put-scaling-policy \
  --auto-scaling-group-name my-app-asg \
  --policy-name cpu-target-tracking \
  --policy-type TargetTrackingScaling \
  --target-tracking-configuration '{
    "PredefinedMetricSpecification": {
      "PredefinedMetricType": "ASGAverageCPUUtilization"
    },
    "TargetValue": 50.0
  }'
```

### 9.5 Health Checks

| Type | Checks | Default |
|------|--------|---------|
| EC2 | Is the instance running? (system status checks) | Always on |
| ELB | Is the instance passing load balancer health checks? | Must be enabled |

Set `--health-check-type ELB` when behind a load balancer. Otherwise, an instance can be "running" but unresponsive and the ASG will not replace it.

## 10. Pricing Models

### 10.1 Comparison

| Model | Commitment | Discount | Best For |
|-------|-----------|----------|----------|
| **On-Demand** | None | 0% | Short-term, unpredictable, testing |
| **Reserved Instances** | 1 or 3 years | Up to 72% | Steady-state, known baseline |
| **Savings Plans** | 1 or 3 years ($/hr commitment) | Up to 72% | Flexible across instance families/regions |
| **Spot Instances** | None (can be interrupted) | Up to 90% | Fault-tolerant, batch, CI/CD, stateless workers |
| **Dedicated Hosts** | On-Demand or Reserved | Varies | Licensing, compliance, regulatory |

### 10.2 Spot Instances

Spot instances use **spare AWS capacity** at steep discounts. AWS can reclaim them with a **2-minute warning**.

```bash
# Launch a spot instance
aws ec2 run-instances \
  --instance-type c5.xlarge \
  --instance-market-options '{"MarketType": "spot", "SpotOptions": {"SpotInstanceType": "one-time"}}' \
  --image-id ami-0abc123

# Check current spot prices
aws ec2 describe-spot-price-history \
  --instance-types c5.xlarge \
  --product-descriptions "Linux/UNIX" \
  --start-time "$(date -u +%Y-%m-%dT%H:%M:%S)" \
  --query 'SpotPriceHistory[].{AZ:AvailabilityZone,Price:SpotPrice}' \
  --output table
```

**Best practices for Spot:**

- Use multiple instance types and AZs to reduce interruption risk
- Handle the 2-minute interruption notice gracefully (drain connections, checkpoint state)
- Use Spot with ASG `MixedInstancesPolicy` to blend On-Demand and Spot
- Never run databases or stateful workloads on Spot

### 10.3 Savings Plans vs Reserved Instances

| Aspect | Reserved Instances | Savings Plans |
|--------|-------------------|---------------|
| Scope | Specific instance type in specific region | Compute (any instance, any region) or EC2-specific |
| Flexibility | Low (locked to instance family) | High (commit $/hr, use anywhere) |
| Recommendation | Legacy approach | **Preferred for new commitments** |

## 11. Essential CLI Commands

```bash
# Launch an instance
aws ec2 run-instances \
  --image-id ami-0abc123 \
  --instance-type t3.micro \
  --count 1 \
  --key-name my-key \
  --security-group-ids sg-0abc123 \
  --subnet-id subnet-0abc123

# Describe instances
aws ec2 describe-instances \
  --filters "Name=tag:Env,Values=prod" "Name=instance-state-name,Values=running" \
  --query 'Reservations[].Instances[].{ID:InstanceId,Type:InstanceType,IP:PrivateIpAddress,State:State.Name}'

# Stop, start, and terminate
aws ec2 stop-instances --instance-ids i-0abc123
aws ec2 start-instances --instance-ids i-0abc123
aws ec2 terminate-instances --instance-ids i-0abc123

# Create an AMI
aws ec2 create-image --instance-id i-0abc123 --name "backup-$(date +%F)"

# Describe instance types available
aws ec2 describe-instance-types \
  --filters "Name=instance-type,Values=m5.*" \
  --query 'InstanceTypes[].{Type:InstanceType,vCPUs:VCpuInfo.DefaultVCpus,RAM:MemoryInfo.SizeInMiB}'

# Get instance metadata from inside the instance (IMDSv2)
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/instance-id

# View console output (useful for debugging boot issues)
aws ec2 get-console-output --instance-id i-0abc123 --output text
```

## 12. Common Gotchas

### 12.1 T-Series CPU Credits

The most common surprise for newcomers. If your T3 instance consistently uses more CPU than its baseline, it will exhaust its credits and get throttled. Monitor `CPUCreditBalance` in CloudWatch.

```bash
# Check CPU credit balance
aws cloudwatch get-metric-statistics \
  --namespace AWS/EC2 \
  --metric-name CPUCreditBalance \
  --dimensions Name=InstanceId,Value=i-0abc123 \
  --start-time "$(date -u -v-1H +%Y-%m-%dT%H:%M:%S)" \
  --end-time "$(date -u +%Y-%m-%dT%H:%M:%S)" \
  --period 300 \
  --statistics Average
```

If credits are consistently near zero, upgrade to an M-series instance.

### 12.2 EBS Throughput Limits

EBS volumes have IOPS and throughput limits, but so does the **instance type**. A small instance might bottleneck your fast io2 volume. Check the instance's EBS baseline and maximum bandwidth.

| Instance | EBS Bandwidth |
|----------|--------------|
| t3.micro | Up to 1,536 Mbps (burst) |
| m5.large | Up to 4,750 Mbps |
| m5.xlarge | Up to 4,750 Mbps |
| m5.4xlarge | 4,750 Mbps (dedicated) |

### 12.3 IMDSv2 (Instance Metadata Service)

IMDSv1 was vulnerable to SSRF attacks. **Always enforce IMDSv2**, which requires a session token.

```bash
# Enforce IMDSv2 on launch
aws ec2 run-instances \
  --metadata-options HttpTokens=required,HttpEndpoint=enabled \
  ...

# Enforce IMDSv2 on existing instance
aws ec2 modify-instance-metadata-options \
  --instance-id i-0abc123 \
  --http-tokens required \
  --http-endpoint enabled
```

### 12.4 EBS Volume AZ Lock

An EBS volume is **tied to a single AZ**. You cannot attach a `us-east-1a` volume to an instance in `us-east-1b`. To move data across AZs: create a snapshot, then create a new volume from the snapshot in the target AZ.

### 12.5 Public IP Behavior

- **Auto-assigned public IPs** are released when you stop the instance
- **Elastic IPs** persist across stop/start cycles
- If you need a stable public IP, use an Elastic IP or put instances behind a load balancer (recommended)

### 12.6 Instance Limits

AWS has per-region limits on the number of vCPUs you can run. Check and request increases proactively.

```bash
# Check your current EC2 vCPU limits
aws service-quotas get-service-quota \
  --service-code ec2 \
  --quota-code L-1216C47A
```

### 12.7 Stopping vs Terminating

| Action | Effect |
|--------|--------|
| **Stop** | Instance shuts down. EBS volumes are preserved. You stop paying for compute (still pay for EBS). Can be restarted. May get a different physical host and public IP. |
| **Terminate** | Instance is destroyed. Root EBS volume is deleted by default (unless `DeleteOnTermination=false`). Irreversible. |

Enable **termination protection** on production instances to prevent accidental deletion:

```bash
aws ec2 modify-instance-attribute \
  --instance-id i-0abc123 \
  --disable-api-termination
```
