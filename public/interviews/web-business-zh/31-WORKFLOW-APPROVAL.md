# 工作流与审批系统

## 这是什么？

工作流与审批系统就是把公司里"走流程"这件事搬到线上。请假要领导批、报销要财务审、合同要法务看、上线要技术负责人签字——这些原来靠口头传话、邮件转发、纸质签字的事情，现在用系统来管理：谁发起、谁审批、按什么顺序审、超时怎么办、批完之后触发什么动作。作为开发者，你会在 OA 系统、ERP、CRM、项目管理工具、甚至电商后台里遇到审批需求。本质上，只要业务流程中有"人做决策"的环节，就需要审批系统。

## 为什么要懂？

审批系统看起来简单——不就是"提交→审批→通过/驳回"吗？但实际上，它是最容易被低估复杂度的系统之一。你以为是两三个状态，结果上线后发现：审批人请假了谁来代审？多个部门需要同时审批怎么办？流程变更后正在进行中的单据用旧流程还是新流程？审批超时了自动通过还是自动驳回？这些问题处理不好，轻则流程卡死没人管，重则合同未经审批就执行、费用未经核实就打款——造成真实的业务损失和合规风险。

## 业务流程

### 申请发起

1. **发起人**选择流程模板（请假、报销、采购、合同审批等）
2. 填写表单信息：金额、事由、附件、关联单据等
3. 系统根据表单内容和发起人信息**自动匹配审批链**（如金额 > 5万走总监审批，否则走经理审批）
4. 提交后生成唯一的**工单编号**，状态变为"审批中"

### 状态机

审批单据的核心状态流转：

```
草稿(Draft) → 审批中(Pending) → 已通过(Approved)
                    ↘ 已驳回(Rejected) → 重新提交 → 审批中
                    ↘ 已撤回(Withdrawn)
                    ↘ 已超时(Expired)
```

每次状态变更都必须记录：操作人、时间戳、变更前状态、变更后状态、操作备注。状态机的转换规则必须严格定义——不能从"已通过"跳到"草稿"，不能从"已撤回"跳到"已通过"。

### 审批链

审批链定义了一个申请需要经过哪些节点、由谁审批、按什么顺序。

- **固定审批链**：流程模板中预设好审批人（如：直属经理 → 部门总监 → 财务）
- **动态审批链**：根据表单内容在运行时计算（如：金额 < 1万只需经理，1万-10万加总监，> 10万加 VP）
- **多级审批**：逐级上报，每级审批人不同

### 单据流转

单据在审批链中的流转过程：

1. 系统将单据推送到当前审批节点对应的审批人待办列表
2. 审批人查看单据详情、历史审批意见、关联附件
3. 审批人做出决策：通过、驳回（需填写原因）、转交他人
4. 通过后单据流转到下一个节点；驳回后回到发起人或上一节点
5. 所有节点都通过后，单据状态变为"已通过"，触发后续动作

### 基于角色的审批

审批人不一定是具体的某个人，而是某个**角色**：

- **按角色**：审批人 = 发起人所在部门的"部门经理"角色
- **按组织架构**：审批人 = 发起人的直属上级的直属上级
- **按职能**：特定节点固定由"法务专员"或"财务主管"角色审批
- **好处**：人员变动时只需调整角色绑定，不用修改每条流程定义

### 串行与并行审批

- **串行审批**：A 审完 → B 审 → C 审。必须按顺序，前一个没完成后一个看不到单据
- **并行审批（会签）**：A、B、C 同时审批。全部通过才算通过（AND 逻辑），任一驳回则整体驳回
- **并行审批（或签）**：A、B、C 同时审批。任一通过即算通过（OR 逻辑）
- **混合模式**：先并行会签（法务 + 财务同时审），再串行（CEO 最终签字）

### 条件分支

根据单据内容走不同的审批路径：

- **金额分支**：< 1万走快速通道（仅经理），> 1万走完整流程（经理 → 总监 → VP）
- **类型分支**：技术采购走 CTO 审批链，市场采购走 CMO 审批链
- **区域分支**：海外业务额外经过合规审批节点
- **实现方式**：条件表达式引擎（规则引擎），运行时求值决定下一个节点

### SLA 时效管理

每个审批节点设置最大处理时间（SLA）：

1. 单据到达审批人后开始计时（通常只算工作时间，排除周末和节假日）
2. **临期提醒**：SLA 还剩 25% 时发送催办通知
3. **超时升级**：超过 SLA 自动升级到审批人的上级，或自动转交给备选审批人
4. **自动处理**：根据业务规则，超时后自动通过或自动驳回
5. SLA 数据用于管理层分析审批效率瓶颈

### 代理审批与委托

审批人不在时的替代方案：

- **临时委托**：审批人出差/请假前，将审批权限委托给指定同事，设定委托时间范围
- **永久代理**：为关键角色配置固定的备选审批人
- **自动转交**：超时未处理时，系统自动转交给预设的代理人
- **委托记录**：所有委托操作必须记录在案，审计时可追溯"谁替谁审的"

### 审计日志

审批系统必须保留完整的操作轨迹：

- 每一步操作记录：操作人、操作时间、操作类型（提交/通过/驳回/转交/撤回）、IP 地址
- 表单数据变更记录：修改前的值、修改后的值、修改人
- 审批意见全文保留，不可编辑删除
- 日志不可篡改（追加写入，禁止更新和删除）
- 满足企业内部审计和外部合规检查要求

### 通知触发

审批流程中的关键事件自动触发通知：

| 事件         | 通知对象       | 通知渠道                |
| ------------ | -------------- | ----------------------- |
| 新单据待审批 | 审批人         | 站内信、邮件、企微/钉钉 |
| 审批通过     | 发起人         | 站内信、邮件            |
| 审批驳回     | 发起人         | 站内信、邮件、短信      |
| 即将超时     | 当前审批人     | 邮件、即时通讯          |
| 已超时升级   | 上级审批人     | 邮件、短信              |
| 流程全部完成 | 发起人、相关方 | 站内信、邮件            |

### 流程模板

流程模板是审批系统的核心配置单元：

- **表单模板**：定义需要填写哪些字段（文本、数字、日期、下拉、附件等）
- **审批链模板**：定义节点顺序、每个节点的审批人规则、串行/并行模式
- **条件规则**：定义分支条件和跳转逻辑
- **通知模板**：定义各事件的通知内容和渠道
- **权限配置**：谁可以发起这个流程、谁可以查看

### 流程版本管理

流程定义会随业务变化而调整，必须做好版本管理：

- 每次修改流程模板生成新版本（v1、v2、v3...）
- **已发起的单据继续使用发起时的流程版本**（不能半路换规则）
- 新发起的单据使用最新发布的版本
- 可以回滚到历史版本
- 版本变更记录：谁改的、改了什么、什么时候生效

## 常见术语

| 术语            | 含义                                                                            |
| --------------- | ------------------------------------------------------------------------------- |
| **工单/工作单** | 一个具体的审批请求实例，包含表单数据和审批状态                                  |
| **审批链**      | 一条审批请求需要经过的所有审批节点的有序集合                                    |
| **会签**        | 多个审批人同时审批，全部通过才算通过                                            |
| **或签**        | 多个审批人同时审批，任一通过即算通过                                            |
| **加签**        | 审批过程中临时增加一个审批人（当前审批人觉得需要额外的人看一下）                |
| **转签**        | 审批人将单据转交给其他人审批                                                    |
| **驳回**        | 审批人不同意，单据退回给发起人或上一节点                                        |
| **撤回**        | 发起人主动取消已提交的审批请求                                                  |
| **SLA**         | Service Level Agreement，服务时效承诺，这里指审批处理的最长允许时间             |
| **状态机**      | 定义单据所有可能状态及其合法转换路径的模型                                      |
| **流程引擎**    | 驱动审批流转的核心组件，负责路由、条件判断、超时处理等                          |
| **BPMN**        | Business Process Model and Notation，业务流程建模与标注，一种可视化流程定义标准 |
| **规则引擎**    | 负责执行条件分支判断的组件，根据输入数据输出路由决策                            |
| **代理审批**    | 某人代替原审批人进行审批操作                                                    |
| **催办**        | 系统或人工提醒审批人尽快处理待审单据                                            |

## 常见模式

### 模式一：基于 BPMN 的可视化流程设计

用 BPMN 标准定义审批流程，提供拖拽式流程设计器，业务人员（非开发者）可以自己配置和修改审批流程。

**适用场景：** 流程频繁变化、流程种类多（几十甚至上百种）的大中型企业。

**代表产品：** Camunda、Flowable、Activiti、钉钉审批。

**取舍：** 灵活性极高，但引擎本身的学习和维护成本也高。小团队慎用。

### 模式二：硬编码审批链

审批逻辑直接写在代码里：`if (amount > 50000) { approvers = [manager, director, vp] }`。

**适用场景：** 流程简单且稳定、只有几种审批类型的小型团队或早期产品。

**取舍：** 开发快，但每次调整流程都要改代码、测试、上线。流程变多后维护成本急剧上升。

### 模式三：配置驱动的审批链

审批规则存储在数据库或配置文件中，代码实现通用的流程引擎，流程定义通过管理后台配置。

**适用场景：** 中等复杂度，流程偶尔调整，不需要 BPMN 那么重的方案。

**取舍：** 平衡了灵活性和复杂度。大多数 SaaS 产品的审批模块采用这种模式。

### 模式四：事件驱动的异步审批

每个审批动作发布事件到消息队列，后续节点监听事件并触发处理。审批结果通过事件通知下游系统（如审批通过后自动触发打款、发货、开通权限等）。

**适用场景：** 审批系统需要与多个下游系统联动的场景。

**取舍：** 解耦性好，但调试和排查问题更复杂。需要完善的事件追踪和重试机制。

## 踩坑提醒

- **审批人离职没处理**：审批链里绑的是具体用户 ID，该用户离职后单据永远卡在这个节点。必须用角色而非具体人，或者有离职交接流程自动转移待办。
- **并行节点的驳回逻辑没想清楚**：A 和 B 并行审批，A 通过了 B 驳回了——算通过还是驳回？通过的那条怎么回滚？上线前必须和业务方确认清楚。
- **状态机转换没有守卫**：代码里直接 `status = 'approved'` 而不检查当前状态是否允许转换。应该用状态机库或者严格的校验逻辑，杜绝非法状态跳转。
- **流程变更影响在途单据**：修改了审批流程后，正在审批中的单据突然找不到下一个节点了。在途单据必须沿用发起时的流程版本。
- **SLA 只算自然时间不算工作时间**：周五下午 5 点提交，SLA 24 小时，周六早上就超时了。SLA 计时应该扣除非工作时间和节假日。
- **审计日志可以被修改**：审批记录存在普通业务表里，有权限的人可以改。审计日志必须追加写入、禁止更新删除，最好用独立的日志存储。
- **通知轰炸**：一个审批人同时有 50 条待审，每条都发邮件 + 短信 + 钉钉通知。必须做通知合并和频率控制——比如每 30 分钟汇总一次。
- **没有考虑撤回的时机**：发起人在审批人已经通过后才撤回，但下游系统已经执行了。撤回操作必须检查当前流程进度，已触发下游动作的不能简单撤回。
- **条件分支测试不充分**：金额判断写成 `amount > 10000`，忽略了刚好等于 10000 的情况。所有边界条件必须有对应的测试用例。

## 速查表

| 场景                | 推荐方案                                                |
| ------------------- | ------------------------------------------------------- |
| 简单审批（< 5 种）  | 配置驱动的审批链 + 数据库存储流程定义                   |
| 复杂审批（> 20 种） | BPMN 流程引擎（Camunda / Flowable）+ 可视化设计器       |
| 审批人匹配          | 基于角色 + 组织架构动态解析，避免绑定具体用户 ID        |
| 并行审批            | 明确定义会签（AND）还是或签（OR），以及驳回时的回滚策略 |
| 条件分支            | 规则引擎或表达式解析器，支持运行时动态求值              |
| 超时处理            | SLA 计时（仅工作时间）+ 临期提醒 + 超时自动升级/转交    |
| 代理审批            | 委托机制 + 时间范围限定 + 完整委托记录                  |
| 通知系统            | 多渠道（站内信 + 邮件 + IM）+ 通知合并 + 频率控制       |
| 审计合规            | 追加写入的不可变日志 + 独立存储 + 操作人/时间/IP 全记录 |
| 流程版本管理        | 版本号递增 + 在途单据绑定发起时版本 + 可回滚            |
| 下游联动            | 事件驱动架构 + 审批通过后发布事件 + 下游系统订阅消费    |
| 流程设计工具        | Camunda Modeler、钉钉审批设计器、自建拖拽式设计器       |
