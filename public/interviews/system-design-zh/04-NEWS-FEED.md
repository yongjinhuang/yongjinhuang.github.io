# 设计新闻动态系统 (Twitter/Facebook)

新闻动态是用户主页中间不断更新的故事列表。
它聚合了用户关注的人和页面的帖子，按相关性排序，并
提供个性化体验。这是最常被问到的系统设计
问题之一，因为它涉及 Fan-out 策略、缓存、排序和大规模扩展。

---

## 1. 需求澄清

### 功能需求

| ID  | 需求                               | 描述                                                           |
| --- | ---------------------------------- | -------------------------------------------------------------- |
| F1  | 发布帖子                           | 用户可以创建文本、图片和视频帖子                               |
| F2  | 查看个性化动态                     | 用户看到来自关注对象的聚合动态                                 |
| F3  | 关注 / 取消关注                    | 用户可以关注和取消关注其他用户                                 |
| F4  | 点赞 / 评论                        | 用户可以对帖子进行点赞和评论                                   |
| F5  | 媒体支持                           | 帖子可以包含图片、视频和带预览的链接                           |
| F6  | 动态刷新                           | 用户可以下拉刷新查看新帖子                                     |
| F7  | 分页                               | 无限滚动，支持高效分页                                         |

### 非功能需求

| ID   | 需求                   | 目标                                                          |
| ---- | ---------------------- | ------------------------------------------------------------- |
| NF1  | 动态延迟               | 动态生成和检索 p99 < 500ms                                    |
| NF2  | 一致性模型             | 最终一致性（动态更新略有延迟是可接受的）                      |
| NF3  | 可用性                 | 99.99% 正常运行时间（CAP 定理中的 AP 系统）                   |
| NF4  | 持久性                 | 已发布帖子零数据丢失                                          |
| NF5  | 可扩展性               | 处理 3 亿 DAU 及流量高峰                                      |

### 规模估算

```
DAU:                    300,000,000
每用户平均关注数:       300
每日平均发帖数(活跃):   5 帖/天 (10% 的用户是活跃发帖者)
活跃发帖者:             30,000,000
每日总帖子数:           150,000,000  (~1,750 帖/秒 平均, ~5,000 帖/秒 峰值)

每日动态读取:           3 亿用户 * 10 次打开/天 = 3,000,000,000 次读取/天
动态读取 QPS:           ~35,000 次读取/秒 平均, ~100,000 次读取/秒 峰值

Fan-out 每日写入:       1.5 亿帖子 * 300 平均粉丝 = 45,000,000,000 次 Fan-out 写入
Fan-out 写入 QPS:       ~520,000 次写入/秒 平均

存储（帖子/年）:
  - 文本: 1.5 亿帖/天 * 1KB 平均 = 150GB/天 = 55TB/年
  - 媒体: 1.5 亿 * 20% 带媒体 * 2MB 平均 = 60TB/天 = 22PB/年

动态缓存 (Redis):
  - 3 亿用户 * 500 帖子 ID * 8 字节 = ~1.2TB
```

## 2. API 设计

### 2.1 发布帖子

```
POST /v1/feed/publish
Authorization: Bearer <token>

Request Body:
{
  "content": "Hello world! Check out this photo.",
  "media_ids": ["media_abc123", "media_def456"],
  "visibility": "public",          // public | followers | private
  "reply_to": null                  // post_id if this is a reply
}

Response: 201 Created
{
  "post_id": "post_789xyz",
  "created_at": "2025-01-15T10:30:00Z",
  "status": "published"
}
```

媒体通过预签名 URL 流程单独上传，然后再调用发布接口：

```
POST /v1/media/upload
Authorization: Bearer <token>

Request Body: multipart/form-data (file)

Response: 200 OK
{
  "media_id": "media_abc123",
  "upload_url": "https://cdn.example.com/upload/...",
  "status": "processing"
}
```

### 2.2 获取个性化动态

```
GET /v1/feed?cursor=<cursor>&limit=20
Authorization: Bearer <token>

Response: 200 OK
{
  "posts": [
    {
      "post_id": "post_789xyz",
      "author": { "user_id": "u123", "name": "Alice", "avatar_url": "..." },
      "content": "Hello world!",
      "media": [{ "type": "image", "url": "..." }],
      "like_count": 42,
      "comment_count": 7,
      "liked_by_me": false,
      "created_at": "2025-01-15T10:30:00Z"
    }
  ],
  "next_cursor": "eyJ0IjoxNzA1MzEyMjAwfQ==",
  "has_more": true
}
```

### 2.3 关注 / 取消关注

```
POST   /v1/follow/{userId}        // 关注用户
DELETE /v1/follow/{userId}        // 取消关注用户
GET    /v1/follow/{userId}/followers?cursor=...&limit=20
GET    /v1/follow/{userId}/following?cursor=...&limit=20
```

### 2.4 点赞 / 评论

```
POST   /v1/posts/{postId}/like
DELETE /v1/posts/{postId}/like
POST   /v1/posts/{postId}/comments   { "text": "Great post!" }
GET    /v1/posts/{postId}/comments?cursor=...&limit=20
```

### 2.5 基于游标的分页 vs 基于偏移量的分页

```
基于偏移量:  GET /feed?offset=20&limit=10
基于游标:    GET /feed?cursor=abc123&limit=10
```

| 方面                 | 基于偏移量                      | 基于游标                            |
| -------------------- | ----------------------------- | --------------------------------- |
| 插入新项目           | 重复 / 跳过项目                | 无重复                              |
| 性能                 | O(n) - 扫描跳过的行            | O(1) - 定位到游标位置               |
| 一致性               | 实时插入时会中断                | 在数据变动中保持稳定                 |
| 实现复杂度           | 简单                          | 略为复杂                             |
| 适用场景             | 静态数据集                     | 实时动态（我们的选择）               |

**游标格式**：Base64 编码的 JSON，包含最后返回项目的时间戳或排序键。
服务器解码后将其用作 WHERE 子句的边界。

```
Cursor = base64({ "created_at": "2025-01-15T10:30:00Z", "post_id": "post_789xyz" })
Query: SELECT * FROM feed WHERE (created_at, post_id) < (decoded_ts, decoded_id)
       ORDER BY created_at DESC, post_id DESC LIMIT 20
```

## 3. 数据模型

### 3.1 用户表 (PostgreSQL)

```sql
CREATE TABLE users (
    user_id       BIGINT PRIMARY KEY,
    username      VARCHAR(50) UNIQUE NOT NULL,
    display_name  VARCHAR(100),
    email         VARCHAR(255) UNIQUE NOT NULL,
    avatar_url    VARCHAR(500),
    bio           TEXT,
    follower_count   INT DEFAULT 0,
    following_count  INT DEFAULT 0,
    is_celebrity     BOOLEAN DEFAULT FALSE,   -- 用于混合 Fan-out 的标记
    created_at    TIMESTAMP DEFAULT NOW(),
    updated_at    TIMESTAMP DEFAULT NOW()
);

-- 当 follower_count > 500,000 时，用户被标记为名人
```

### 3.2 帖子表 (PostgreSQL，按 user_id 分片)

```sql
CREATE TABLE posts (
    post_id       BIGINT PRIMARY KEY,       -- Snowflake ID（包含时间戳）
    author_id     BIGINT NOT NULL,
    content       TEXT,
    visibility    VARCHAR(20) DEFAULT 'public',
    reply_to      BIGINT,                    -- 如果不是回复则为 NULL
    like_count    INT DEFAULT 0,
    comment_count INT DEFAULT 0,
    share_count   INT DEFAULT 0,
    created_at    TIMESTAMP DEFAULT NOW(),

    INDEX idx_author_time (author_id, created_at DESC)
);
```

### 3.3 关注表 (PostgreSQL，按 follower_id 分片)

```sql
CREATE TABLE follows (
    follower_id   BIGINT NOT NULL,
    followee_id   BIGINT NOT NULL,
    created_at    TIMESTAMP DEFAULT NOW(),

    PRIMARY KEY (follower_id, followee_id),
    INDEX idx_followee (followee_id, follower_id)
);

-- "用户 X 关注了谁?"  -> WHERE follower_id = X
-- "谁关注了用户 Y?"   -> WHERE followee_id = Y
```

### 3.4 动态缓存结构 (Redis Sorted Set)

```
Key:    feed:{user_id}
Type:   Sorted Set
Score:  帖子时间戳（或排序分数）
Value:  post_id

示例:
  ZADD feed:u123 1705312200 "post_abc"
  ZADD feed:u123 1705312100 "post_def"
  ZADD feed:u123 1705312000 "post_ghi"

读取:   ZREVRANGEBYSCORE feed:u123 +inf -inf LIMIT 0 20
大小:   每用户仅保留最新 800 条记录（使用 ZREMRANGEBYRANK 裁剪）
TTL:    7 天（过期后访问时重新预热）
```

### 3.5 点赞表

```sql
CREATE TABLE likes (
    user_id    BIGINT NOT NULL,
    post_id    BIGINT NOT NULL,
    created_at TIMESTAMP DEFAULT NOW(),
    PRIMARY KEY (user_id, post_id),
    INDEX idx_post (post_id)
);
```

### 3.6 评论表

```sql
CREATE TABLE comments (
    comment_id  BIGINT PRIMARY KEY,
    post_id     BIGINT NOT NULL,
    author_id   BIGINT NOT NULL,
    content     TEXT NOT NULL,
    created_at  TIMESTAMP DEFAULT NOW(),

    INDEX idx_post_time (post_id, created_at DESC)
);
```

### 3.7 媒体表

```sql
CREATE TABLE media (
    media_id    BIGINT PRIMARY KEY,
    post_id     BIGINT,
    uploader_id BIGINT NOT NULL,
    media_type  VARCHAR(20),          -- image, video, gif
    url         VARCHAR(500) NOT NULL,
    thumbnail   VARCHAR(500),
    width       INT,
    height      INT,
    size_bytes  BIGINT,
    status      VARCHAR(20) DEFAULT 'processing',
    created_at  TIMESTAMP DEFAULT NOW(),

    INDEX idx_post (post_id)
);
```

### 3.8 数据库选择理由

| 数据               | 存储选择        | 原因                                                         |
| ------------------ | --------------- | ------------------------------------------------------------ |
| 用户               | PostgreSQL      | 对配置文件的强一致性，ACID 事务                              |
| 帖子               | PostgreSQL      | 结构化数据，关系查询，按 author_id 分片                      |
| 关注               | PostgreSQL      | 图查询，双向查找，事务性计数                                 |
| 动态缓存           | Redis           | 超低延迟读取，用于排序的 Sorted Set                          |
| 媒体元数据         | PostgreSQL      | 与帖子的关系联接                                             |
| 媒体文件           | S3 + CDN        | Blob 存储，全球分布式                                        |
| 点赞 / 评论        | PostgreSQL      | 事务完整性，计数准确性                                       |
| 活动日志           | Cassandra       | 高写入吞吐量，时间序列，仅追加                               |
| 搜索索引           | Elasticsearch   | 帖子内容全文搜索                                             |

### 两个主要流程

**流程 1 - 动态发布（写入路径）：**
```
用户创建帖子
  -> API Gateway
    -> Post Service（验证，存储到数据库）
      -> Kafka（Fan-out 主题）
        -> Fan-out Service（将 post_id 写入粉丝的动态缓存）
        -> Notification Service（推送通知）
        -> Search Indexer（为搜索建立索引）
```

**流程 2 - 动态读取（读取路径）：**
```
用户打开应用 / 滚动动态
  -> API Gateway
    -> Feed Service
      -> 检查动态缓存 (Redis)
        -> 如果命中: 返回缓存的动态条目
        -> 如果未命中: 查询关注者的帖子，排序，缓存，返回
      -> 将 post_id 填充为完整的帖子数据
      -> 实时合并名人帖子（混合模型）
      -> 返回排序的、分页的动态
```

## 5. 动态发布深入探讨

动态系统的核心设计决策是 **Fan-out 策略**：何时以及如何
将新帖子分发到所有粉丝的动态中？

### 5.1 写时 Fan-out（推模型）

当用户发布帖子时，立即将 post_id 推送到
每个粉丝的动态缓存中。

```
               用户 A 发布帖子 P
                       │
                       ▼
              ┌─────────────────┐
              │  Post Service   │
              │  (存储帖子)      │
              └────────┬────────┘
                       │
                       ▼
              ┌─────────────────┐
              │  Fan-out Worker │
              │  (通过 Kafka    │
              │   异步处理)      │
              └────────┬────────┘
                       │
          ┌────────────┼────────────┐
          │            │            │
          ▼            ▼            ▼
   ┌────────────┐ ┌────────────┐ ┌────────────┐
   │feed:userB  │ │feed:userC  │ │feed:userD  │
   │ + post P   │ │ + post P   │ │ + post P   │
   │(Redis ZADD)│ │(Redis ZADD)│ │(Redis ZADD)│
   └────────────┘ └────────────┘ └────────────┘
        ...对用户 A 的所有 N 个粉丝执行
```

**步骤：**
1. Post Service 验证并将帖子存储到 Posts 数据库。
2. Post Service 向 Kafka 发布事件：`{ post_id, author_id }`。
3. Fan-out 工作节点消费该事件。
4. 对于作者的每个粉丝，执行 `ZADD feed:{follower_id} <timestamp> <post_id>`。
5. 将每个动态裁剪到最新 800 条：`ZREMRANGEBYRANK feed:{follower_id} 0 -801`。

### 5.2 读时 Fan-out（拉模型）

发布时不做任何操作。当用户打开动态时，
实时查询其关注的所有人的帖子。

```
               用户 B 请求动态
                       │
                       ▼
              ┌─────────────────┐
              │  Feed Service   │
              └────────┬────────┘
                       │
           ┌───────────┼───────────┐
           │           │           │
           ▼           ▼           ▼
    ┌────────────┐ ┌────────────┐ ┌────────────┐
    │ 用户 A 的  │ │ 用户 C 的  │ │ 用户 D 的  │
    │ 帖子       │ │ 帖子       │ │ 帖子       │
    │ (查询 DB)  │ │ (查询 DB)  │ │ (查询 DB)  │
    └─────┬──────┘ └─────┬──────┘ └─────┬──────┘
          │              │              │
          └──────────────┼──────────────┘
                         │
                         ▼
                ┌─────────────────┐
                │   合并 + 排序   │
                │   + 分页        │
                └─────────────────┘
                         │
                         ▼
                   返回动态
```

**步骤：**
1. Feed Service 查找用户 B 关注了谁（从关注表或缓存）。
2. 对每个被关注者，获取其最新的 N 条帖子。
3. 合并所有帖子，按分数排序，返回顶部页面。

### 5.3 混合方案（推荐）

对普通用户使用**写时 Fan-out**，对名人使用**读时 Fan-out**。

```
                用户发布帖子
                        │
                        ▼
                ┌───────────────┐
                │ Post Service  │
                └───────┬───────┘
                        │
                        ▼
               ┌─────────────────┐
               │ 作者是否为       │
               │ 名人？           │
               │ (>50 万粉丝)    │
               └──┬───────────┬──┘
                  │           │
              否  │           │  是
                  ▼           ▼
         ┌──────────────┐  ┌──────────────────┐
         │ 写时 Fan-out │  │ 仅存储帖子。      │
         │ 到所有粉丝的 │  │ 不执行 Fan-out。  │
         │ 动态缓存     │  │ 帖子将在读取时    │
         └──────────────┘  │ 合并。            │
                           └──────────────────┘

                    --- 读取时 ---

         ┌──────────────────────────────────┐
         │ Feed Service 读取用户的动态      │
         │                                  │
         │ 1. 获取预计算的动态（缓存）      │
         │ 2. 获取用户关注的名人列表        │
         │ 3. 获取每个名人的最新帖子        │
         │ 4. 合并 + 重新排序               │
         │ 5. 返回分页结果                  │
         └──────────────────────────────────┘
```

### 5.4 策略对比

| 方面                | 写时 Fan-out（推）              | 读时 Fan-out（拉）             | 混合                           |
| ------------------- | ----------------------------- | ---------------------------- | ------------------------------ |
| 写延迟              | 高（Fan-out 到所有粉丝）       | 低（仅存储帖子）               | 中等                           |
| 读延迟              | 低（预计算）                   | 高（读取时计算）               | 低（大部分预计算）             |
| 名人问题            | 严重（数百万次写入）           | 无                             | 已解决（名人用拉模型）         |
| 存储成本            | 高（重复 post_id）             | 低                             | 中等                           |
| 新鲜度              | 接近实时                       | 始终最新                       | 接近实时                       |
| 非活跃用户          | 浪费写入                       | 无浪费                         | 已优化（缓存有 TTL）           |
| 复杂度              | 简单                           | 简单                           | 更复杂                         |
| 最适合              | 中小规模用户                   | 有大量名人的系统               | 大规模生产系统                 |

### 5.5 Fan-out 写入量计算

```
对于拥有 300 个粉丝的普通用户：
  1 条帖子 -> 300 次 Redis ZADD 操作
  时间：~300 * 0.1ms = 30ms（流水线处理时更少）

对于拥有 1000 万粉丝的名人：
  1 条帖子 -> 10,000,000 次 Redis ZADD 操作
  时间：~1000 万 * 0.1ms = 1,000 秒（不可接受！）

  使用混合方案：0 次 Fan-out 写入。在每个读者的读取时合并。
  读取时成本：~5-10 次名人帖子获取，每次 ~2ms = 额外 10-20ms
```

## 6. 动态排序

### 6.1 时间序 vs 算法排序

| 方式           | 优点                               | 缺点                              |
| -------------- | ---------------------------------- | --------------------------------- |
| 时间序         | 简单、透明、实时                   | 低互动率，垃圾内容占主导          |
| 算法排序       | 更高互动率，个性化                 | 复杂，有"信息茧房"风险            |

大多数现代动态使用**算法排序**，并提供切换到时间序的选项。

### 6.2 简单排序公式

一个在面试中效果不错的基础评分函数：

```
Score = Affinity * TimeDecay * PostTypeWeight * QualityScore

其中：
  Affinity      = 衡量读者与作者互动程度的指标
  TimeDecay     = 1 / (1 + age_hours * decay_rate)
  PostTypeWeight = 基于帖子类型的权重（图片 > 文本，视频 > 图片）
  QualityScore  = 归一化的互动信号
```

**亲密度分数计算：**

```
Affinity(reader, author) =
    w1 * like_frequency        // 读者点赞作者帖子的频率
  + w2 * comment_frequency     // 读者评论作者帖子的频率
  + w3 * profile_view_freq     // 读者查看作者主页的频率
  + w4 * message_frequency     // 他们互相发消息的频率
  + w5 * recency_of_follow     // 最近关注 = 更高亲密度

典型权重：w1=0.3, w2=0.3, w3=0.15, w4=0.15, w5=0.10
```

**时间衰减函数：**

```
TimeDecay(age_hours) = 1 / (1 + 0.1 * age_hours)

示例：
  0 小时前：  1.0
  1 小时前：  0.91
  6 小时前：  0.63
  24 小时前：0.29
  72 小时前：0.12
```

**帖子类型权重：**

```
video_with_engagement:  1.5
image_post:             1.3
link_with_preview:      1.1
text_post:              1.0
reshare:                0.8
```

**质量分数：**

```
QualityScore = normalize(
    likes * 1.0
  + comments * 3.0        // 评论是更强的信号
  + shares * 5.0          // 分享是最强的信号
  - hides * -10.0         // 负面信号
  - reports * -50.0       // 强负面信号
)
```

### 6.3 基于 ML 的排序流水线

对于生产系统，排序是一个多阶段的 ML 流水线：

```
    所有候选帖子 (~2000)
              │
              ▼
    ┌──────────────────┐
    │  阶段 1：        │   轻量级模型，缩减到 ~500 个候选
    │  候选筛选        │   特征：作者亲密度、帖子年龄、帖子类型
    │                  │
    └────────┬─────────┘
             │
             ▼
    ┌──────────────────┐
    │  阶段 2：        │   中等模型，为每个候选评分
    │  粗排序          │   特征：互动预测、内容质量
    │  (评分 ~500)     │
    └────────┬─────────┘
             │
             ▼
    ┌──────────────────┐
    │  阶段 3：        │   重型模型（深度神经网络）
    │  精排序          │   特征：完整特征集、交叉特征
    │  (排序前 ~100)   │   输出：P(点赞), P(评论), P(分享), P(点击)
    └────────┬─────────┘
             │
             ▼
    ┌──────────────────┐
    │  阶段 4：        │   业务规则、多样性注入
    │  重新排序 /      │   - 同一作者不超过 2 条帖子
    │  策略层          │   - 在位置 3, 8, 15... 插入广告
    └────────┬─────────┘   - 提升新内容类型
             │             - 降权标题党
             ▼

        (返回前 20 条)

### 7.2 动态缓存结构（Redis 详情）

```
# 每用户动态缓存（Sorted Set）
Key:     feed:{user_id}
Score:   ranking_score（时间序排序时使用时间戳）
Member:  post_id

# 操作：
ZADD     feed:u123 1705312200 "post_abc"      # 添加帖子到动态
ZREVRANGE feed:u123 0 19                       # 获取前 20 条帖子
ZREVRANGEBYSCORE feed:u123 <cursor_score> -inf LIMIT 0 20  # 游标分页
ZCARD    feed:u123                             # 动态大小
ZREMRANGEBYRANK feed:u123 0 -801               # 仅保留前 800 条

# 每用户关注的名人列表（Set）
Key:     celeb_following:{user_id}
Members: 名人 user_id

SMEMBERS celeb_following:u123                  # 获取用户关注的名人

# 帖子缓存（Hash）
Key:     post:{post_id}
Fields:  author_id, content, media, like_count, comment_count, created_at

HGETALL post:post_abc                          # 获取完整帖子数据
```

### 7.3 基于游标的分页实现

```
第 1 页请求：
  GET /v1/feed?limit=20

  服务端：
    ZREVRANGEBYSCORE feed:u123 +inf -inf LIMIT 0 21   # 获取 21 条以检查 has_more
    last_item_score = items[19].score
    last_item_id = items[19].post_id
    next_cursor = base64({ "s": last_item_score, "id": last_item_id })
    has_more = (len(items) == 21)
    return items[0:20], next_cursor, has_more

第 2 页请求：
  GET /v1/feed?cursor=eyJzIjoxNzA1MzEyMjAwLCJpZCI6InBvc3RfYWJjIn0=&limit=20

  服务端：
    decoded = decode(cursor)  # { "s": 1705312200, "id": "post_abc" }
    # 使用复合键避免并列
    ZREVRANGEBYSCORE feed:u123 (1705312200 -inf LIMIT 0 21
    # 如果分数相同，按 post_id < cursor.id 过滤
    ...
```

### 7.4 动态填充

动态缓存中存储的 Post ID 是轻量级的。我们需要将它们"填充"为
完整的帖子对象。这通过批量多键获取完成：

```
输入：  [post_id_1, post_id_2, ..., post_id_20]

步骤 1：检查帖子缓存 (Redis MGET)
  MGET post:id_1 post:id_2 ... post:id_20
  -> 返回缓存的帖子 + 缓存未命中的

步骤 2：对于缓存未命中的，批量查询 Posts 数据库
  SELECT * FROM posts WHERE post_id IN (miss_1, miss_2, ...)
  -> 回填到帖子缓存

步骤 3：批量获取作者信息
  MGET user:author_1 user:author_2 ...
  -> 同样的未命中回填模式

步骤 4：检查当前用户是否点赞了每条帖子
  Pipeline: SISMEMBER likes:post_id_1 current_user_id
            SISMEMBER likes:post_id_2 current_user_id
            ...

步骤 5：组装完整的响应对象
```

## 8. 名人 / 热门用户问题

### 8.1 问题

考虑一个拥有 5000 万粉丝、每天发帖 10 次的名人：

```
每条帖子的 Fan-out 写入次数：  50,000,000
每天的 Fan-out 写入次数：      500,000,000
每条帖子 Fan-out 时间：        5000 万 * 0.1ms / 流水线 = ~50 秒

在这 50 秒内：
  - Redis 集群承受大量写入负载
  - 粉丝的动态部分更新（不一致）
  - 其他 Fan-out 操作被排队和延迟
  - 系统整体动态新鲜度下降
```

### 8.2 混合方案详情

```
┌───────────────────────────────────────────────────────┐
│                名人分类                                 │
│                                                       │
│  阈值：follower_count > 500,000                       │
│  更新：批处理任务每天运行，也在关注事件时触发          │
│  存储：用户表上的 is_celebrity 标记 + 缓存             │
│                                                       │
│  ~0.1% 的用户是名人 = ~30 万用户                      │
│  这 30 万用户产生了 ~20% 的所有消费内容                │
└───────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────┐
│            发帖时（对于名人）                           │
│                                                       │
│  1. 将帖子存储到 Posts 数据库       （与往常相同）     │
│  2. 添加到名人的帖子时间线 (Redis list)               │
│     LPUSH celeb_posts:{author_id} post_id             │
│     LTRIM celeb_posts:{author_id} 0 99                │
│  3. 不执行到粉丝的 Fan-out                            │
│  4. 可选择仅通知"超级粉丝"                            │
└───────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────┐
│          读取时（合并名人帖子）                         │
│                                                       │
│  1. 从缓存读取预计算的动态（普通帖子）                │
│  2. 获取用户关注的名人列表：                          │
│     SMEMBERS celeb_following:{user_id}                │
│  3. 对每个名人（通常每用户 5-20 个）：                │
│     LRANGE celeb_posts:{celeb_id} 0 9                 │
│     （获取每个名人最新的 10 条帖子）                   │
│  4. 将名人帖子合并到动态中                            │
│  5. 重新排序合并后的集合                              │
│  6. 返回前 N 条                                       │
│                                                       │
│  额外读取延迟：~5-20ms（可接受）                      │
└───────────────────────────────────────────────────────┘
```

### 8.3 优化：名人帖子缓存

```
# 预计算的"热门名人帖子"缓存
# 由后台工作节点每 30 秒更新

Key:    trending_celeb_posts
Type:   Sorted Set
Score:  engagement_velocity（likes_per_minute * comment_weight）
Member: post_id

# 关注很多名人的用户将此作为补充
# 将逐个名人查找减少为单个 Sorted Set 读取
```

### 9.2 缓存失效策略

```
事件：新帖子发布
  -> Fan-out 服务将 post_id 添加到粉丝的动态缓存（ZADD）
  -> 不需要失效（追加操作）

事件：帖子删除
  -> 从作者的帖子缓存中移除：DEL post:{post_id}
  -> 异步：从所有包含它的动态缓存中移除
     （或让它过期，读取时如果帖子不存在则过滤）

事件：帖子编辑
  -> 更新帖子缓存：HSET post:{post_id} content "new content"
  -> 动态缓存只存储 post_id，因此不需要动态失效

事件：用户取消关注作者
  -> 从粉丝的动态缓存中移除作者的帖子（代价高）
  -> 替代方案：读取时过滤（返回前检查关注表）
  -> 懒惰方案：让帖子自然地从 800 条记录窗口中过期

事件：用户资料更新
  -> 失效用户缓存：DEL user:{user_id}
  -> 如果头像改变则 CDN 清除
```

### 9.3 缓存预热

```
活跃用户检测：
  - 过去 24 小时内至少打开一次应用的用户
  - ~60% 的 DAU = ~1.8 亿用户

缓存预热策略：
  ┌─────────────────────────────────────────┐
  │  后台工作节点（持续运行）                 │
  │                                          │
  │  1. 从 Kafka 消费新帖子事件              │
  │  2. 对于活跃粉丝：                      │
  │     -> 立即 Fan-out（高优先级）          │
  │  3. 对于非活跃粉丝：                    │
  │     -> 跳过 Fan-out（节省资源）          │
  │     -> 在下次登录时预热其缓存            │
  │                                          │
  │  用户登录时（如果缓存是冷的）：          │
  │  1. 获取关注列表                         │
  │  2. 并行获取最新帖子                     │
  │  3. 排序并缓存                           │
  │  4. 时间：~200-500ms（对于长时间未登录    │
  │     后的首次加载是可接受的）              │
  └─────────────────────────────────────────┘
```

### 10.2 消息队列架构 (Kafka)

```
┌───────────────────────────────────────────────────────┐
│                  KAFKA 拓扑                            │
│                                                       │
│  Topic: post-events                                   │
│  分区：128                                            │
│  分区键：author_id                                    │
│  保留期：7 天                                         │
│  消费者：Fan-out 工作节点（128 个实例）               │
│                                                       │
│  Topic: fanout-tasks                                  │
│  分区：256                                            │
│  分区键：target_user_id                               │
│  用途：单独的 Fan-out 操作                            │
│  消费者：Feed-write 工作节点（256 个实例）            │
│                                                       │
│  Topic: notifications                                 │
│  分区：64                                             │
│  分区键：target_user_id                               │
│  消费者：Notification 工作节点（64 个实例）           │
│                                                       │
│  流程：                                               │
│  post-events -> Fan-out Service -> fanout-tasks       │
│                                 -> notifications      │
│                                 -> search-indexing    │
│                                 -> analytics          │
└───────────────────────────────────────────────────────┘
```

**为什么 Fan-out 按 target_user_id 分区：**
- 对同一用户动态的所有写入都经过同一分区
- 防止对单个用户动态缓存的竞态条件
- 支持按用户有序处理

### 11.2 跨区域一致性挑战

| 挑战                      | 解决方案                                                     |
| ------------------------- | ------------------------------------------------------------ |
| 用户在美国发帖，粉丝在欧洲阅读 | 异步复制，延迟 <500ms；对动态而言可接受                  |
| 用户资料更新              | 写入主节点（US-EAST），复制到所有区域                        |
| 关注/取消关注             | 写入主节点，在所有区域异步调整 Fan-out                       |
| 动态缓存不一致            | 每个区域维护自己的动态缓存，本地填充                         |
| 名人帖子传播              | 通过 MirrorMaker 发布到所有区域的 Kafka 集群                 |
| 冲突解决                  | 对边缘情况使用向量时钟的最后写入者获胜策略                   |

**一致性模型：**
- 帖子：写入主区域，~200-500ms 内复制
- 动态缓存：最终一致，从本地副本按区域构建
- 用户资料：通过粘性会话到主节点保证读自己的写
- 关注图：最终一致（关注后动态更新有短暂延迟）

### 12.1 如何处理实时动态更新？

```
选项 A：长轮询
  - 客户端每 30 秒轮询：GET /v1/feed/updates?since=<timestamp>
  - 服务器保持连接打开直到有新帖子或超时
  - 简单，在代理后面可用
  - 延迟：0-30 秒

选项 B：Server-Sent Events (SSE)
  - 客户端打开持久连接：GET /v1/feed/stream
  - 服务器推送新帖子通知
  - 单向的，轻量级
  - 适合 Web 客户端

选项 C：WebSockets
  - 双向持久连接
  - 服务器实时推送动态更新
  - 更高的资源成本（持久连接）
  - 最适合类聊天体验

推荐：SSE 用于动态更新
  ┌────────┐        ┌────────────┐        ┌───────────┐
  │ Client │<──SSE──│ Feed Push  │<──Sub──│  Redis     │
  │        │        │ Service    │        │  Pub/Sub   │
  └────────┘        └────────────┘        └───────────┘
                                               ▲
                                               │ Publish
                                          ┌────┴──────┐
                                          │ Fan-out   │
                                          │ Service   │
                                          └───────────┘

  流程：
  1. Fan-out 服务发布到 Redis Pub/Sub 频道：user:{user_id}:feed
  2. Feed Push Service 订阅已连接用户的频道
  3. 有新消息时，向客户端推送 SSE 事件
  4. 客户端接收并在动态 UI 中前置显示

  规模考虑：
  - 不是所有用户都需要实时（~10% 正在主动查看动态）
  - 使用在线检测仅为活跃用户维护连接
  - 连接限制：每台服务器 ~100 万并发 SSE 连接（经过调优）
  - 对于 3000 万并发用户：30 台 Feed Push 服务器
```

### 12.2 如何实现热门话题？

```
架构：
  ┌───────────────┐     ┌────────────────┐     ┌──────────────┐
  │  帖子流        │────>│ 话题提取器      │────>│ 热门话题      │

  - Hashtag 提取（显式信号）

  TrendingScore = (mentions_last_hour - mentions_baseline) / mentions_baseline

  - 全球热门：所有用户的热门话题

## 13. 总结：关键设计决策

| 决策点                     | 我们的选择                     | 理由                                   |
| -------------------------- | ------------------------------ | -------------------------------------- |
| Fan-out 策略               | 混合（推 + 拉）                | 处理名人问题而不浪费资源               |
| 动态存储                   | Redis Sorted Set               | 亚毫秒读取，按排名排序                 |
| 分页                       | 基于游标                       | 在实时插入下保持稳定                   |
| 排序                       | 算法排序（ML 流水线）          | 比时间序排序有更高互动率               |
| 帖子数据库                 | PostgreSQL（分片）             | ACID，成熟工具链，广泛理解             |
| 消息队列                   | Kafka                          | 高吞吐量，持久化，分区                 |
| 缓存失效                   | 写穿 + TTL                     | 最终一致性是可接受的                   |
| 名人阈值                   | 50 万粉丝                     | 经验性地平衡成本与新鲜度               |
| 多区域                     | 按区域主备                     | 延迟优化的读取，集中写入               |
| 实时更新                   | SSE                            | 轻量级，对动态足够用                   |
| 内容审核                   | 多层（规则 + ML + 人工）       | 平衡速度和准确性                       |

## 15. 面试技巧

1. **从需求开始。** 在深入设计之前澄清范围。询问关于
   规模、一致性需求以及哪些功能在范围内。

2. **识别核心问题。** 新闻动态问题的本质是
   **Fan-out 策略**。确保尽早讨论推 vs 拉 vs 混合方案。

3. **做数学计算。** 粗略估算表明为什么写时 Fan-out 对
   名人不可行（每帖 5000 万次写入），以及为什么需要混合方案。

4. **明确讨论权衡取舍。** 每个设计选择都有权衡取舍。指出它们：
   一致性 vs 可用性，存储 vs 计算，延迟 vs 新鲜度。

5. **画清晰的图表。** 将写入路径（发布）与读取路径
   （动态检索）分开。这使架构更容易理解。

6. **分层缓存。** CDN -> 应用 -> Redis -> 数据库。解释每一层的命中率和
   失效策略。

7. **主动提出名人问题。** 面试官喜欢探究这一点。
   准备好混合方案及具体数据。

8. **以监控结束。** 提到关键指标：动态延迟 p99、Fan-out 延迟、
   缓存命中率、错误率。展示你对生产系统的思考。
