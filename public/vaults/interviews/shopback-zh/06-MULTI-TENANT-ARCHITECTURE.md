# 系统设计：服务 13 个市场的多租户架构

> ShopBack 正在积极从按市场独立部署迁移到多租户架构。这是一个主要的 BREW（更好的工程周）计划。

## 1. 背景与问题

### 之前：按市场独立部署

```
┌──────────┐  ┌──────────┐  ┌──────────┐     ┌──────────┐
│ SG 栈    │  │ MY 栈    │  │ ID 栈    │ ... │ US 栈    │
│          │  │          │  │          │     │          │
│ ┌──────┐ │  │ ┌──────┐ │  │ ┌──────┐ │     │ ┌──────┐ │
│ │ API  │ │  │ │ API  │ │  │ │ API  │ │     │ │ API  │ │
│ │ DB   │ │  │ │ DB   │ │  │ │ DB   │ │     │ │ DB   │ │

└──────────┘  └──────────┘  └──────────┘     └──────────┘
 AWS ap-se-1   AWS ap-se-1   AWS ap-se-3      AWS us-east-1
```

**存在的问题：**

- 11 个独立技术栈分布在 5 个 AWS 区域
- 每个市场需要单独的基础设施部署
- 启动新市场需要数周/数月
- 功能发布是顺序进行的（逐个市场部署）
- 每个服务需要为自己的流量峰值预留资源
- 市场之间没有共享的经验和配置
- 200+ 名工程师维护碎片化的工具

### 之后：多租户架构

## 2. 需求

### 功能性需求

- 单一代码库服务所有 13 个市场
- 按市场配置（货币、语言、商家、功能）
- 市场级数据隔离（用户、交易）
- 新市场上线从数月缩短到数天
- 功能开关实现按市场渐进发布

### 非功能性需求

- **噪声邻居防护**：一个市场的流量激增不影响其他市场
- **数据驻留**：某些市场要求数据存储在本区域
- **延迟**：市场本地请求 < 100ms
- **可用性**：市场级故障隔离
- **合规性**：各市场法规要求

## 4. 架构深入探讨

### 4.1 租户感知的请求流程

```
┌──────┐    ┌──────────┐    ┌────────────┐    ┌──────────┐
│用户  │───→│API       │───→│ 租户       │───→│ 服务     │
│sg.app│    │网关      │    │ 解析器     │    │ 层       │
└──────┘    └──────────┘    └────────────┘    └─────┬────┘
                                                     │
                                                     ▼
                                              ┌────────────┐
                                              │ 租户感知   │
                                              │ 数据库     │
                                              │ 路由器     │
                                              └────────────┘
```

**租户解析：**

```typescript
interface TenantContext {
  tenantId: string; // 'sg', 'my', 'id' 等
  currency: string; // 'SGD', 'MYR', 'IDR'
  locale: string; // 'en-SG', 'ms-MY', 'id-ID'
  timezone: string; // 'Asia/Singapore'
  region: string; // 'ap-southeast-1'
  features: string[]; // 启用的功能开关
  dataResidency: string; // 'shared' | 'regional' | 'isolated'
}

// 解析来源：
// 1. 域名：sg.shopback.com → tenant: 'sg'
// 2. 请求头：X-Market-Id: sg
// 3. 路径：/api/v1/sg/deals
// 4. JWT 声明：{ market: 'sg' }
```

### 4.2 数据库设计（共享 Schema）

```sql
-- 每张表都包含 market 列以实现租户隔离
CREATE TABLE users (
    user_id     BIGINT GENERATED ALWAYS AS IDENTITY,
    market      VARCHAR(2) NOT NULL,
    email       VARCHAR(255) NOT NULL,
    name        VARCHAR(255),
    created_at  TIMESTAMPTZ DEFAULT NOW(),

    PRIMARY KEY (market, user_id),
    UNIQUE (market, email)
);

-- 行级安全策略实现租户隔离
ALTER TABLE users ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON users
    USING (market = current_setting('app.current_market'));

-- 每次请求前：
SET app.current_market = 'sg';
-- 现在所有查询自动过滤到 'sg' 的数据
```

**按市场分区：**

```sql
-- 大表按市场分区以提升性能
CREATE TABLE transactions (
    txn_id      UUID DEFAULT gen_random_uuid(),
    market      VARCHAR(2) NOT NULL,
    user_id     BIGINT NOT NULL,
    amount      DECIMAL(12,2) NOT NULL,
    currency    VARCHAR(3) NOT NULL,
    created_at  TIMESTAMPTZ DEFAULT NOW()
) PARTITION BY LIST (market);

CREATE TABLE transactions_sg PARTITION OF transactions FOR VALUES IN ('sg');
CREATE TABLE transactions_my PARTITION OF transactions FOR VALUES IN ('my');
CREATE TABLE transactions_id PARTITION OF transactions FOR VALUES IN ('id');
-- ... 每个市场类似
```

## 5. 噪声邻居防护

### 问题

新加坡的双十一流量激增不应拖慢马来西亚的正常运行。

### 解决方案

```
┌─────────────────────────────────────────────┐
│            资源隔离                           │
│                                             │
│  级别 1：每租户限流                          │
│  级别 2：每租户独立线程池                    │
│  级别 3：资源配额（CPU、内存）              │
│  级别 4：活动期间为高流量租户               │
│           单独分配计算资源                    │
└─────────────────────────────────────────────┘
```

**限流：**

```
每租户限制：
  sg：10,000 请求/秒（最高流量市场）
  my：5,000 请求/秒
  id：8,000 请求/秒
  ...

活动期间：
  sg：50,000 请求/秒（自动扩展）
  其他：不变
```

**数据库连接池：**

```
总连接池：200 个连接

分配：
  sg：50 个连接（25%）
  my：30 个连接（15%）
  id：40 个连接（20%）
  预留：30 个连接（15%）-- 突发容量
  其他：50 个连接（25%）-- 其余市场共享
```

## 6. 迁移策略

### 阶段一：共享服务（低风险）

- 先迁移只读服务（商家目录、优惠列表）
- 新旧技术栈读取相同数据
- 功能开关控制路由

### 阶段二：写路径迁移

- 双写期：写入同时发送到新旧系统
- 验证数据一致性
- 逐步将读流量切换到新系统

### 阶段三：全面切换

- 停止向旧系统写入
- 最终数据同步
- DNS 切换
- 旧系统保持待命 30 天

```
时间线：
第 1-2 月：共享只读服务（商家、优惠）
第 3-4 月：用户服务迁移
第 5-6 月：交易服务迁移
第 7-8 月：按市场全面切换（先新加坡，再其他）
第 9 月+：停用旧技术栈
```

## 7. 关键权衡

| 决策                                  | 考虑因素                                       |
| ------------------------------------- | ---------------------------------------------- |
| 共享 vs 独立数据库                    | 共享降低成本，独立用于有法规要求的市场         |
| 行级安全 vs 应用层过滤               | RLS 更安全但增加查询开销                       |
| 按市场分区                            | 查询性能更好，但迁移更难                       |
| 集中式 vs 分布式配置                  | 集中保证一致性，本地缓存降低延迟               |
| 功能开关复杂度                        | 更灵活但增加运维开销                           |
