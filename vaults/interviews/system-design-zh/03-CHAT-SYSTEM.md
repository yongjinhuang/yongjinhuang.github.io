## 1. 需求澄清

### 功能需求

| 功能           | 描述                                 |
| -------------- | ------------------------------------ |
| 一对一聊天     | 两个用户之间的实时消息通信           |
| 群聊           | 支持最多 500 名成员的群组对话        |
| 在线/离线状态  | 实时显示用户在线状态                 |
| 已读回执       | 每条消息的已发送、已送达、已读指示器 |
| 媒体共享       | 图片、视频、文件、语音消息           |
| 消息历史       | 持久化存储，支持回滚/搜索            |
| 推送通知       | 当用户离线时通知新消息               |
| 多设备同步     | 消息同时在手机、平板、桌面端可用     |
| 正在输入指示器 | 显示联系人正在输入                   |

### 非功能需求

| 需求     | 目标                                   |
| -------- | -------------------------------------- |
| 延迟     | 端到端消息投递 < 200ms                 |
| 可靠性   | 无消息丢失——保证投递                   |
| 有序性   | 消息在对话中按正确顺序展示             |
| 离线支持 | 为离线用户排队消息，重新连接时投递     |
| 可用性   | 99.99% 正常运行时间 (< 52 分钟停机/年) |
| 安全性   | 一对一端到端加密，全面 TLS             |
| 一致性   | 可接受最终一致性（秒级内）             |

### 规模估算

```
日活用户 (DAU):                 500,000,000
每用户每日消息数:               80
每日总消息量:                   500M * 80 = 40,000,000,000 (40B)
每秒消息数 (平均):             40B / 86,400 ≈ 463,000 msg/s
每秒消息数 (峰值 3 倍):       ~1,400,000 msg/s

平均消息大小:                   200 bytes (文本)
每日文本存储量:                 40B * 200B = 8 TB/天
年度文本存储量:                 8 TB * 365 = ~2.9 PB/年

媒体消息 (总量的 10%):          4B/天
平均媒体大小:                   500 KB
每日媒体存储量:                 4B * 500KB = 2 PB/天

并发 WebSocket 连接数:          ~150M (任意时刻 DAU 的 30%)
```

### 带宽估算

```
文本入站带宽:    463K msg/s * 200B = ~93 MB/s = ~744 Mbps
文本出站带宽:    ~2 倍入站 (扇出) = ~1.5 Gbps
媒体入站:        4B / 86400 * 500KB ≈ 23 GB/s
媒体出站 (含 CDN): 分布式，源站约 ~10 GB/s
```

## 2. 通信协议

### 协议比较

```
+------------------+----------+-----------+-------------+----------+
|   协议           | 延迟     | 服务器    | 双向通信     | 浏览器   |
|                  |          | 负载      |              | 支持     |
+------------------+----------+-----------+-------------+----------+
| HTTP Polling     | 高       | 非常高    | 否           | 是       |
| Long Polling     | 中       | 高        | 否 (模拟)    | 是       |
| Server-Sent      | 低       | 中        | 否 (仅服务器 | 是       |
|   Events (SSE)   |          |           |   -> 客户端) |          |
| WebSocket        | 非常低   | 低        | 是           | 是       |
+------------------+----------+-----------+-------------+----------+
```

### 为什么其他方案不够理想（WebSocket 除外）

**HTTP Polling:**

- 客户端按固定间隔发送请求（例如每 3 秒）。
- 浪费资源：大多数响应为空；大规模下产生巨大负载。
- 1.5 亿连接每 3 秒轮询一次 = 每秒 5000 万次纯开销请求。

**Long Polling:**

- 客户端发起请求；服务器保持连接直到有数据可用或超时。
- 比轮询好，但每个消息周期仍需创建新的 TCP 连接。
- 非真正双向：客户端在每次响应后必须发送新请求。
- 超时管理复杂。

**Server-Sent Events (SSE):**

- 单向：仅服务器到客户端。客户端仍需使用 HTTP 发送消息。
- 适合信息流/通知，但聊天需要真正的双向通信。
- 旧版浏览器中每个域限制约 6 个并发连接。

**WebSocket（最佳选择）:**

- 全双工、持久 TCP 连接。
- 握手后开销极小（每帧头部约 2 字节）。
- 在单一连接上实现真正的双向通信。
- 所有现代浏览器和移动平台原生支持。

### 回退策略

```
1. 尝试 WebSocket 连接
   |
   ├── 成功 -> 使用 WebSocket（首选）
   |
   └── 失败（企业代理、防火墙）
       |
       ├── 尝试 SSE + HTTP POST 组合
       |   |
       |   ├── 成功 -> 使用 SSE 接收，HTTP POST 发送
       |   |
       |   └── 失败
       |       |
       |       └── 回退到 Long Polling
       |
       └── 移动端：使用平台推送（APNs/FCM）作为最后手段
```

## 4. 数据模型

### 为什么选择 Cassandra / HBase 存储消息？

| 特性         | Cassandra 的优势                       |
| ------------ | -------------------------------------- |
| 写密集型     | 463K 写入/秒——Cassandra 擅长顺序写入   |
| 时间序列数据 | 消息天然按时间排序；非常适合 LSM 树    |
| 分区容错     | AP 系统；优雅地容忍网络分区            |
| 线性扩展     | 添加节点以处理更多吞吐量，无需重新分片 |
| 无复杂连接   | 聊天查询很简单：按对话 + 时间获取消息  |
| TTL 支持     | 自动过期临时消息（动态、阅后即焚）     |

### 用户表 (PostgreSQL -- 关系型数据)

```sql
CREATE TABLE users (
    user_id         BIGINT PRIMARY KEY,      -- Snowflake ID
    username        VARCHAR(32) UNIQUE NOT NULL,
    display_name    VARCHAR(64),
    email           VARCHAR(128) UNIQUE,
    phone           VARCHAR(20) UNIQUE,
    avatar_url      VARCHAR(512),
    public_key      TEXT,                     -- 用于 E2E 加密
    status_message  VARCHAR(256),
    created_at      TIMESTAMP DEFAULT NOW(),
    updated_at      TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_users_phone ON users(phone);
CREATE INDEX idx_users_email ON users(email);
```

### 对话表 (PostgreSQL)

```sql
CREATE TABLE conversations (
    conversation_id   BIGINT PRIMARY KEY,     -- Snowflake ID
    type              VARCHAR(10) NOT NULL,    -- 'direct' 或 'group'
    name              VARCHAR(128),            -- 直接对话为 NULL，群组设置名称
    avatar_url        VARCHAR(512),
    creator_id        BIGINT REFERENCES users(user_id),
    created_at        TIMESTAMP DEFAULT NOW(),
    updated_at        TIMESTAMP DEFAULT NOW()
);
```

### 对话成员表 (PostgreSQL)

```sql
CREATE TABLE conversation_members (
    conversation_id   BIGINT REFERENCES conversations(conversation_id),
    user_id           BIGINT REFERENCES users(user_id),
    role              VARCHAR(16) DEFAULT 'member',  -- 'admin', 'member'
    nickname          VARCHAR(64),
    joined_at         TIMESTAMP DEFAULT NOW(),
    muted_until       TIMESTAMP,
    PRIMARY KEY (conversation_id, user_id)
);

CREATE INDEX idx_members_user ON conversation_members(user_id);
```

### 消息表 (Cassandra)

```sql
CREATE TABLE messages (
    conversation_id   BIGINT,
    message_id        BIGINT,          -- Snowflake ID (按时间排序)
    sender_id         BIGINT,
    message_type      TEXT,            -- 'text', 'image', 'video', 'file', 'voice'
    content           TEXT,            -- 文本内容或媒体 URL
    metadata          TEXT,            -- JSON：缩略图、尺寸、时长等
    reply_to_id       BIGINT,          -- 用于线程回复
    is_deleted        BOOLEAN,
    created_at        TIMESTAMP,
    PRIMARY KEY (conversation_id, message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
```

**分区策略：**

- **分区键**: `conversation_id` -- 对话中的所有消息在同一节点上。
- **聚簇键**: `message_id` (DESC) -- 最新消息优先检索。
- 对于非常活跃的群组，使用复合分区：`(conversation_id, time_bucket)`，其中 `time_bucket = message_id / 1_000_000`，以防止热分区。

### 消息状态表 (Cassandra)

```sql
CREATE TABLE message_status (
    conversation_id   BIGINT,
    message_id        BIGINT,
    user_id           BIGINT,
    status            TEXT,            -- 'sent', 'delivered', 'read'
    updated_at        TIMESTAMP,
    PRIMARY KEY ((conversation_id, user_id), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
```

### 用户对话表 (Cassandra -- 用于收件箱)

```sql
CREATE TABLE user_conversations (
    user_id             BIGINT,
    last_message_at     TIMESTAMP,
    conversation_id     BIGINT,
    last_message_preview TEXT,
    unread_count        INT,
    PRIMARY KEY (user_id, last_message_at)
) WITH CLUSTERING ORDER BY (last_message_at DESC);
```

### 索引策略

```
+---------------------------+-----------------------------------+
| 查询模式                  | 索引/表设计                       |
+---------------------------+-----------------------------------+

+---------------------------+-----------------------------------+
```

## 5. 核心流程

### 5.1 一对一消息发送流程

```
用户 A (发送方)       Chat Server A       Kafka       Chat Server B       用户 B (接收方)
     |                      |                |               |                    |
     | 1. WS Frame:         |                |               |                    |
     |    {msg, to:B,       |                |               |                    |
     |     text:"Hello"}    |                |               |                    |
     |--------------------->|                |               |                    |
     |                      |                |               |                    |
     | 2. ACK (msg_id,      |                |               |                    |
     |    status:sent)       |                |               |                    |
     |<---------------------|                |               |                    |
     |                      |                |               |                    |
     |                      | 3. 发布到      |               |                    |
     |                      |    msg.send    |               |                    |
     |                      |    topic       |               |                    |
     |                      |--------------->|               |                    |
     |                      |                |               |                    |
     |                      |                | 4. 消费       |                    |
     |                      |                |    消息       |                    |
     |                      |                |-------------->|                    |
     |                      |                |               |                    |
     |                      |                |    5. 查找：用户 B 是否连接       |
     |                      |                |       到此服务器？                 |
     |                      |                |               |                    |
     |                      |                |               | 6. 是：通过       |
     |                      |                |               |    WebSocket 转发  |
     |                      |                |               |------------------->|
     |                      |                |               |                    |
     |                      |                |               | 7. 投递 ACK       |
     |                      |                |               |<-------------------|
     |                      |                |               |                    |
     |                      |                |<--------------|                    |
     |                      |<---------------|               |                    |
     | 8. 状态更新：         |                |               |                    |
     |    已送达             |                |               |                    |
     |<---------------------|                |               |                    |
     |                      |                |               |                    |

     如果用户 B 在第 5 步时离线：
     |                      |                |               |                    |
     |                      |                | 4b. 存入      |                    |
     |                      |                |     离线      |                    |
     |                      |                |     队列      |                    |
     |                      |                |               |                    |
     |                      |                | 4c. 发送推送  |                    |
     |                      |                |     通知      |                    |
     |                      |                |------------------------------------>|
     |                      |                |               |           (手机)   |
```

**逐步说明：**

1. 用户 A 通过与 Chat Server A 的 WebSocket 连接发送消息。
2. Chat Server A 生成 `message_id`（Snowflake ID），将消息持久化到 Cassandra，并立即向用户 A 发送状态为 `sent` 的 ACK。
3. Chat Server A 将消息发布到 `msg.send` Kafka topic。
4. 负责用户 B 分区的消费者接收消息。
5. 消费者检查服务发现（ZooKeeper/etcd）或 Redis 连接注册表，查找持有用户 B WebSocket 连接的 Chat Server。
6. 如果用户 B 在线，消息通过其 Chat Server 的 WebSocket 转发。
7. 用户 B 的客户端通过 WebSocket 发送投递 ACK。
8. 投递状态回传至用户 A，UI 从单勾更新为双勾。

## 6. 消息投递保证

### 投递语义比较

```
+-------------------+------------------+---------------------+
| 保证级别          | 行为             | 使用场景            |
+-------------------+------------------+---------------------+
| 至多一次          | 发后即忘。       | 正在输入指示器      |
|                   | 可能丢失消息。   | (丢失可接受)        |
+-------------------+------------------+---------------------+
| 至少一次          | 重试直到 ACK。   | 聊天消息            |
|                   | 可能重复。       | (配合去重)          |
+-------------------+------------------+---------------------+
| 恰好一次          | 无丢失，无重复。 | 支付消息            |
|                   | 代价非常高。     | (在聊天规模下       |
|                   |                  |  不实际)            |
+-------------------+------------------+---------------------+
```

**我们的选择：至少一次 + 幂等性 = 实质上恰好一次。**

### 消息 ID 生成 (Snowflake ID)

```
64 位 Snowflake ID 结构：
┌──────────┬────────────┬──────────────┬──────────────┐
│  1 bit   │  41 bits   │   10 bits    │  12 bits     │
│  (符号)  │ (时间戳)   │ (机器 ID)    │ (序列号)     │
│  未使用  │ (距 epoch  │              │              │
│          │  的毫秒数) │              │              │
└──────────┴────────────┴──────────────┴──────────────┘

特性：
- 按时间排序：     后生成的 ID 总是更大
- 全局唯一：       服务器间无需协调
- K-可排序：       可按时间顺序排序
- 紧凑：           64 位适合 BIGINT 列
- 高吞吐量：       每台机器每毫秒 4096 个 ID（12 位序列号）

示例：
  时间戳 (41 bits):  距自定义 epoch 的当前毫秒数
  机器 ID (10 bits):  标识 chat server（最多 1024 台）
  序列号 (12 bits):   每毫秒计数器（最多 4096）

  总容量：1024 台机器 * 4096 IDs/ms = ~42 亿 IDs/秒
```

### 消息排序

**问题：** 分布式系统可能会乱序投递消息。

**解决方案：** 每个对话的序列号。

```
对话 C 有一个单调递增的计数器：

  来自 A 的消息：seq=1, "嘿"
  来自 B 的消息：seq=2, "你好"
  来自 A 的消息：seq=3, "你好吗？"
  来自 B 的消息：seq=4, "挺好，你呢？"

客户端渲染逻辑：
  1. 缓冲收到的消息
  2. 按 (conversation_id, sequence_number) 排序
  3. 如果检测到间隙（收到 seq=5 但缺少 seq=4）：
     a. 在缓冲区中保留 seq=5
     b. 向服务器请求缺失的 seq=4
     c. 间隙填补后按序显示
  4. 超时：3 秒后乱序显示并重新排序

服务端排序：
  - 每个对话在 Redis 中有一个原子计数器：
      INCR conversation:{conv_id}:seq
  - 在处理时分配，而非发送时
  - 保证对话内的严格排序
```

## 7. 群聊设计

### 扇出策略

```
策略 1：写时扇出（WhatsApp 风格，适用于小群组）
=============================================================

当用户 A 向群组 G（100 名成员）发送消息时：

  1. 将消息写入 messages 表一次
  2. 扇出服务写入每个成员的收件箱/队列：
     - 写入 user_B 的收件箱
     - 写入 user_C 的收件箱
     - ...
     - 写入 user_100 的收件箱
  3. 每个在线成员通过其 WebSocket 收到推送

优点：
  + 读取速度快（预计算的收件箱）
  + 客户端逻辑简单
  + 低读取延迟

缺点：
  - 写放大：1 条消息 -> N 次写入
  - 大群组代价高（500 名成员 = 500 次写入）
  - 对不活跃用户的写入浪费


策略 2：读时扇出（Slack 风格，适用于频道）
=====================================================

当用户 A 向频道 C（10,000 名成员）发送消息时：

  1. 将消息写入频道的消息流一次
  2. 写入时不进行扇出
  3. 每个用户在打开频道时从频道流中读取

优点：
  + 最小写入代价（无论群组大小只需 1 次写入）
  + 不活跃用户无浪费工作
  + 可扩展到非常大的频道

缺点：
  - 更高的读取延迟（每次打开都必须查询频道）
  - 更复杂的客户端逻辑（合并多个频道）
  - 推送通知需要与消息存储分开处理
```

### 混合策略（推荐）

```
┌─────────────────┬────────────────────┬─────────────────────┐
│ 群组大小        │ 策略               │ 理由                 │
├─────────────────┼────────────────────┼─────────────────────┤
│ 一对一 (2)      │ 写时扇出           │ 代价微不足道         │
│ 小群组 (3-100)  │ 写时扇出           │ 可接受的写放大       │
│                 │                    │                     │
│ 中群组 (100-500)│ 写时扇出           │ 配合写入批处理       │
│                 │ (优化版)           │ 和异步处理           │
│ 大频道 (500+)   │ 读时扇出           │ 写入代价太高；       │
│                 │                    │ 大多数成员不活跃     │
└─────────────────┴────────────────────┴─────────────────────┘
```

### 心跳机制

```
┌────────────────────────────────────────────────────────────┐
│                    心跳协议                                  │
├────────────────────────────────────────────────────────────┤
│                                                            │
│  客户端发送：每 30 秒 WebSocket PING                       │
│  服务器回复：WebSocket PONG                                │
│                                                            │
│  服务端：                                                  │
│    - 每次 PONG 刷新 Redis key 的 TTL 至 60 秒             │
│    - 60 秒无 PING，Redis key 过期 -> 离线                  │
│    - WebSocket 关闭时，立即清理 -> 离线                    │
│                                                            │
│  Redis key:                                                │
│    presence:{user_id} = {server_id, last_active}          │
│    EXPIRE 60                                               │
│                                                            │
│  时间线：                                                  │
│    t=0s   PING ──> PONG, TTL 重置为 60s                    │
│    t=30s  PING ──> PONG, TTL 重置为 60s                    │
│    t=60s  PING ──> PONG, TTL 重置为 60s                    │
│    t=90s  (无 PING -- 用户已断开)                          │
│    t=120s Redis TTL 过期 -> 用户标记为离线                 │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

### 联系人在线状态扇出

```
问题：用户 A 有 500 个联系人。当 A 上线时，
     我们要通知全部 500 人吗？代价太高。

朴素方案：
  A 上线 -> 通知全部 500 个联系人
  500 用户 * 每人 500 联系人 = 250,000 个在线状态事件
  在 1.5 亿在线用户下，这是不可持续的。

优化方案：

  1. 懒加载在线状态
     - 当用户 B 打开与用户 A 的聊天时，
       B 订阅 A 的在线状态频道
     - 仅活跃对话获得在线状态更新

  2. 在线状态分组
     - 在 Redis 中维护"活跃对话伙伴"
     - 仅扇出给最近有交互的用户

  3. 批量在线状态查询
     - 当用户打开联系人列表时，仅批量查询
       可见联系人的在线状态（而非全部 500 个）
     - 对 20 个可见联系人进行 GET presence:{user_id}

实现：
  ┌─────────────┐
  │  Redis Pub/ │
  │  Sub 频道   │
  │             │
  │  Channel:   │
  │  presence:  │
  │  {user_id}  │
  └──────┬──────┘
         │
         │  仅订阅者收到更新：
         │
         ├──> 用户 B (正在与 A 聊天)             ✓ 收到
         ├──> 用户 C (正在与 A 聊天)             ✓ 收到
         ├──> 用户 D (A 在 D 的联系人列表中      ✗ 不收到
         │          但聊天未打开)                    (按需轮询)
         └──> 用户 E (与 A 无关联)               ✗ 未订阅
```

### 端到端加密考量

```
Signal Protocol（WhatsApp 使用）：

  1. 每个用户生成：
     - Identity Key Pair（长期）
     - Signed Pre-Key（中期，每月轮换）
     - One-Time Pre-Keys（临时，单次使用）

  2. 密钥交换 (X3DH)：
     用户 A 想向用户 B 发消息：
       a. A 从服务器获取 B 的公钥
       b. A 执行三重 Diffie-Hellman 导出共享密钥
       c. A 使用共享密钥加密消息
       d. 服务器无法读取消息（无法访问私钥）

  3. Double Ratchet：
     - 每条消息使用一个新的对称密钥
     - 前向保密：泄露当前密钥
       不会暴露过去的消息
     - 后向保密：泄露当前密钥
       不会暴露未来的消息

  媒体加密：
     a. 为每个媒体文件生成随机 AES-256 密钥
     b. 使用 AES-256-CBC 加密媒体
     c. 将加密后的 blob 上传到 S3（服务器只能看到密文）
     d. 在 E2E 加密消息中发送 AES 密钥 + 媒体 URL
     e. 接收方解密消息获取 AES 密钥，然后解密媒体

  ┌────────┐                ┌────────┐               ┌────────┐
  │ 用户 A │                │ 服务器 │               │ 用户 B │
  │        │   加密         │        │   加密        │        │
  │ 明文   │───────────────>│ 无法   │──────────────>│ 明文   │
  │        │   消息         │ 读取   │   消息        │        │
  └────────┘                └────────┘               └────────┘
```

### 优雅的服务器排空

```
部署时将 chat server 下线：

  1. 在服务发现中将服务器标记为"排空中"
  2. 停止接受新连接（LB 从池中移除）
  3. 向所有已连接客户端发送"重新连接"信号
  4. 客户端重新连接到其他健康服务器（带退避策略）
  5. 等待连接数降至 0（或 30 秒超时）
  6. 关闭服务器

  这实现了零停机部署。
```

### 热分区处理（明星群组）

```
问题：一个 500 名成员的群组中某位名人发帖
     会在单个分区上产生巨大的读取流量。

解决方案：

  1. 分桶分区
     原方案：  partition_key = conversation_id
     改为：    partition_key = (conversation_id, time_bucket)

     time_bucket = message_id / 1_000_000

     这将单个对话随时间分散到多个分区，
     防止任何单个分区增长过大。

  2. 读副本
     - 为热门对话添加 Cassandra 读副本
     - 将读查询路由到副本，写入到主节点

  3. 缓存层
     - 在 Redis 中缓存热门对话的最近消息
     - TTL：5 分钟，有新消息时刷新
     - 95%+ 的读取从缓存提供

  4. 速率限制
     - 限制每个用户每个对话的消息速率
     - 例如每用户每分钟最多 30 条消息
     - 防止垃圾消息并减少负载

  热门群组架构：
  ┌────────────┐
  │   客户端   │
  └─────┬──────┘
        │
  ┌─────▼──────┐     ┌──────────────┐

  │   缓存     │     │  95% 的读取  │
  └─────┬──────┘     └──────────────┘
        │
        │ 缓存未命中 (5%)
```

## 12. 常见面试追问

### 如何实现端到端加密？

```
使用 Signal Protocol：

1. 密钥生成（每设备）：
   - Identity Key Pair（永久）
   - Signed Pre-Key（每月轮换）
   - 100 个 One-Time Pre-Keys（单次使用）

2. 初始密钥交换 (X3DH)：
   Alice 想向 Bob 发消息：
   a. Alice 从服务器获取 Bob 的密钥包：
      {identity_key, signed_pre_key, one_time_pre_key}
   b. Alice 使用三重 DH 计算共享密钥：
      DH1 = DH(Alice_identity, Bob_signed_prekey)
      DH2 = DH(Alice_ephemeral, Bob_identity)
      DH3 = DH(Alice_ephemeral, Bob_signed_prekey)
      DH4 = DH(Alice_ephemeral, Bob_one_time_prekey)  [可选]
      SharedSecret = KDF(DH1 || DH2 || DH3 || DH4)

3. Double Ratchet（每条消息）：
   - 对称棘轮：为每条消息导出新密钥
   - DH 棘轮：定期进行新的 DH 交换
   - 结果：每条消息都有唯一的加密密钥

4. 服务器永远看不到明文：
   - 服务器仅存储和转发密文
   - 无法配合基于内容的搜查令
   - 元数据（谁、何时、多少）仍然可见

5. 群组 E2E（Sender Keys）：
   - 每个成员生成一个 Sender Key
   - Sender Key 通过一对一 E2E 通道分发
   - 消息使用 Sender Key 加密一次（高效）
   - 成员加入/离开时重新生成密钥
```

### 如何处理消息搜索？

```
架构：

  ┌──────────┐     ┌──────────────┐     ┌───────────────┐
  │ 消息     │────>│ Kafka topic: │────>│ Elasticsearch │
  │ (Cassan- │     │ msg.search   │     │ Cluster       │
  │  dra)    │     │              │     │               │
  └──────────┘     └──────────────┘     │ 索引：        │
                                        │  - 消息文本   │
                                        │  - 发送者     │
                                        │  - conv_id    │
                                        │  - 时间戳     │
                                        └───────┬───────┘
                                                │
                                        ┌───────▼───────┐
                                        │  搜索 API     │
                                        │               │
                                        │ GET /search?  │
                                        │   q=hello&    │
                                        │   conv_id=C1  │
                                        └───────────────┘

  索引策略：
    - 仅索引用户所属对话的内容
    - 搜索范围限于用户的对话（授权）
    - 使用特定语言的分析器进行分词
    - 写入时索引（近实时，约 1 秒延迟）

  对于 E2E 加密聊天：
    - 服务器无法索引加密内容
    - 客户端搜索：在本地下载并解密消息
    - 或：维护客户端搜索索引（设备上的 SQLite）
```

### 如何跨多设备同步？

```
多设备同步协议：

  1. 设备注册
     每个设备获得唯一的 device_id。
     用户账户有：[device_1, device_2, device_3]

  2. 消息投递
     当消息到达用户 A 时：
       - 投递到用户 A 的所有已连接设备
       - 每个设备独立 ACK 投递
       - 任何设备 ACK 后消息标记为"已送达"

  3. 同步游标（每设备）
     每个设备维护：
       last_synced_msg_id: {conversation_id -> message_id}

     重新连接时：
       设备发送其游标 -> 服务器返回所有更新的消息

  4. 已读同步
     当用户 A 在手机上阅读时：
       - 已读回执发送到服务器
       - 服务器推送"sync:read"事件到用户 A 的平板和桌面端
       - 所有设备更新未读数

  5. 冲突解决
     - 消息是仅追加的（无冲突）
     - 已读状态：取"最新"状态
     - 正在输入指示器：每设备，无需同步
     - 草稿消息：最后写入胜出或仅设备本地

  设备 A (手机)      服务器      设备 B (平板)        设备 C (桌面)
       |                |              |                    |
       | 阅读消息 M5    |              |                    |
       |--------------->|              |                    |
       |                |              |                    |
       |                | 同步已读     |                    |
       |                |------------->|                    |
       |                |              |                    |
       |                | 同步已读     |                    |
       |                |----------------------------------->|
       |                |              |                    |
       |                |   所有设备显示 M5 为已读           |
```

### 如何处理离线用户？

```
离线消息处理：

  1. 检测
     - WebSocket 断开或心跳超时
     - Redis 中的在线状态 key 过期
     - 用户在连接注册表中标记为离线

  2. 消息排队
     当消息到达离线用户时：
       a. 持久化到 Cassandra（始终，无论状态如何）
       b. 添加到离线队列：
          Redis LIST: offline:{user_id} -> [msg_id_1, msg_id_2, ...]
       c. 增加未读计数器：
          Redis HASH: unread:{user_id} -> {conv_id: count}
       d. 触发推送通知

  3. 推送通知
     ┌────────────┐     ┌──────────────┐     ┌────────────┐
     │ 通知       │────>│ APNs (iOS)   │────>│ 用户手机   │
     │ 服务       │     └──────────────┘     └────────────┘
     │            │     ┌──────────────┐     ┌────────────┐
     │            │────>│ FCM (Android)│────>│ 用户手机   │
     └────────────┘     └──────────────┘     └────────────┘

     通知载荷：
       - 发送者姓名
       - 消息预览（前 100 个字符）
       - 对话上下文
       - 角标计数（总未读数）

     通知折叠：
       - 同一对话的多条消息 -> 单条通知
       - "Alice：3 条新消息"

  4. 重连同步
     当用户重新上线时：
       a. 客户端发送每个对话的 last_seen_msg_id
       b. 服务器从 Cassandra 计算差异
       c. 批量投递错过的消息（分页，每批 50 条）
       d. 客户端 ACK 每批 -> 服务器清除离线队列
       e. 用户打开对话时重置未读计数器

  5. 离线时长处理
     - 短暂离线 (< 1 小时)：从离线队列完全同步
     - 中等离线 (1-24 小时)：同步 + 后台预加载
     - 长期离线 (> 24 小时)：优先同步最近的对话，
       滚动时懒加载旧对话
     - 超长离线 (> 30 天)：仅重新同步最近 30 天，
       更早的消息按需可用
```

### 如何实现正在输入指示器？

```
正在输入指示器协议：

  属性：
    - 发后即忘（至多一次投递）
    - 不持久化（临时）
    - 速率限制（每用户每对话每 3 秒最多 1 个事件）
    - 5 秒无更新后自动过期

  流程：
  用户 A (输入中)       Chat Server       用户 B (查看中)
       |                      |                    |
       | 1. {type:"typing",   |                    |
       |     conv_id:"C1",    |                    |
       |     action:"start"}  |                    |
       |--------------------->|                    |
       |                      |                    |
       |                      | 2. 转发             |
       |                      |    (无持久化，      |
       |                      |     无 Kafka)       |
       |                      |------------------->|
       |                      |                    |
       |                      |    3. UI 显示       |
       |                      |    "Alice 正在      |
       |                      |     输入..."        |
       |                      |                    |
       | (用户停止输入)       |                    |
       |                      |                    |
       | 4. {type:"typing",   |                    |
       |     conv_id:"C1",    |                    |
       |     action:"stop"}   |                    |
       |--------------------->|                    |
       |                      |                    |
       |                      | 5. 转发             |
       |                      |------------------->|
       |                      |                    |
       |                      |    6. UI 隐藏       |
       |                      |    输入指示器       |

  群聊优化：
    - 仅发送给已打开对话的成员
    - 在大群组（>50）中显示"3 人正在输入..."
      而非单独的指示器
    - 在服务端聚合输入事件以减少扇出

  客户端逻辑：
    - 开始输入事件：首次按键，然后限制为每 3 秒 1 次
    - 停止输入事件：最后一次按键后 5 秒或消息已发送
    - 接收端：5 秒无更新后自动隐藏指示器
      （处理"停止"事件丢失的情况）
```

## 总结：关键设计决策

```
┌────────────────────────────┬──────────────────────────────────────────┐
│ 决策                       │ 选择与理由                                │
├────────────────────────────┼──────────────────────────────────────────┤
│ 实时协议                   │ WebSocket（全双工、低开销）              │
│ 消息存储                   │ Cassandra（写密集、时间序列）            │
│ 用户/群组元数据            │ PostgreSQL（关系型、强一致性）           │
│ 缓存层                     │ Redis（会话、在线状态、热数据）          │
│ 消息队列                   │ Kafka（解耦、缓冲、重放）               │
│ 媒体存储                   │ S3 + CDN（可扩展、全球分发）            │
│ 消息 ID                    │ Snowflake（按时间排序、分布式）          │
│ 群组 < 500 策略            │ 写时扇出（低读取延迟）                  │
│ 频道 > 500 策略            │ 读时扇出（写入效率）                    │
│ 在线状态                   │ 心跳 + Redis TTL（简单、可靠）          │
│ 多区域                     │ 多活 + 异步复制                         │
│ 投递保证                   │ 至少一次 + 幂等性                       │
│ 排序                       │ 每对话序列号                             │
│ 加密                       │ Signal Protocol（一对一 E2E）           │
│ 搜索                       │ Elasticsearch（全文、近实时）           │
└────────────────────────────┴──────────────────────────────────────────┘
```

### 面试技巧

1. **从需求开始。** 在设计之前明确范围。问："这更像 WhatsApp（移动端、E2E）还是 Slack（频道、集成）？"

2. **尽早提到 WebSocket。** 这是决定性的协议选择。解释为什么轮询在大规模下不可行。

3. **先画高层架构图。** 将 Chat Servers、API Servers、Kafka、存储、在线状态和推送通知作为独立组件展示。

4. **策略性地深入探讨。** 选择 2-3 个领域深入：消息投递流程、群聊扇出和在线状态最具影响力。

5. **明确讨论规模。** 对连接数、存储和带宽进行粗略估算，表明你考虑了现实世界的约束。

6. **不要忘记离线场景。** 只有在双方都在线时才能工作的聊天系统不是真正的聊天系统。离线排队和推送通知是必不可少的。

7. **提及 E2E 加密。** 即使没有被问到，简要提及 Signal Protocol 展示了安全意识，这是高级面试中的差异化因素。

8. **权衡取舍很重要。** 对于每个决策（Cassandra vs MySQL、写时扇出 vs 读时扇出），阐明权衡取舍。没有完美的答案，只有经过充分推理的选择。
